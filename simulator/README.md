# 本地模擬器

在自己的電腦上跑 11 台模擬自駕車，以**外部廠商的身分**接上 SyncDrive T3——
不論那套系統是在 GCP 還是本地。用來驗證整條鏈真的通：

```
伺服器：即時調度引擎 ──MQTT operation/assign──▶ 本機這 11 台車
                                                    │ GET  /order/queryById
                                                    │ PUT  /order/updateOrderProgress
                                                    ▼
伺服器：圖台、對外 ETA ◀──MQTT telemetry / operation──┘
```

車輛只認訂單，**不讀班表**。這條界線是刻意的：換成真車時車端介面完全不變。

---

## 一、開始

```bash
cd simulator
npm install
cp .env.example .env      # 填憑證，見下一節
npm run build:web         # 建置「路線路徑」那一頁，只有改動時才要重跑
npm start
```

打開 <http://127.0.0.1:4300>。

## 二、憑證

全部放 `simulator/.env`（在 `.gitignore` 裡，不會進版控）。值見
[系統帳號與金鑰](../document/系統帳號與金鑰.md)。

| 變數 | 用途 |
|------|------|
| `API_KEY` | 對外 API 的 `x-api-key`（訂單生命週期） |
| `INTERNAL_USER` / `INTERNAL_PASSWORD` | 內部 API 的 Basic Auth（圖資、調度引擎） |
| `MQTT_PMS_01`…`MQTT_PMS_11` | 各車的 MQTT 密碼 |

網頁只顯示「哪幾組已設定」，不顯示值，也不能從網頁修改。要換就改檔案再重開。

**為什麼要一個本地服務，不能只有網頁**：瀏覽器連不了原生 MQTT（只有
WebSocket），而 broker 開的是 1883 的 TCP。而且把 API 金鑰與 11 組車輛密碼放進
網頁，等於把憑證交給任何打得開那一頁的人。

## 三、切換目標

網頁第一區塊。GCP 與本地**只有位址不同**——通道、路徑、認證方式完全一樣。
本地測得過、GCP 測不過的話，差異一定在伺服器，不會是模擬器對兩邊做了不同的事。

| | GCP | 本地 |
|---|---|---|
| MQTT | `34.80.84.224:1883` | `127.0.0.1:1883` |
| 對外 API | `:3100` | `:3100` |
| 內部 API | `:80` | `:3000`（本地沒有 nginx） |

「測試三條通道」會各打一次並回報通不通。連不上時這一頁要能指出是哪一條。

## 四、跑一輪

1. **測試三條通道** —— 四項全通再往下
2. **啟用引擎** —— 伺服器端的調度引擎開始依部署中的班表發訂單
3. **車隊上線** —— 11 台車連上 broker，訂閱 `operation/assign`
4. 看第四區塊的事件：接單 → 執行 → 完成
5. 打開圖台（<http://34.80.84.224/>），車應該在動

順序有關係：**先讓車上線再開引擎**，或至少確認車已連線。指派不會重送，車還沒
連上時發出的訂單就錯過了（引擎有 300 秒補發窗口，超過就跳過）。

停止時反過來：先**停用引擎**，再讓車隊下線。否則引擎會繼續發訂單給沒有人接的車。

## 五、控制項

| 控制 | 說明 |
|------|------|
| 倍速 | 壓縮的是**計畫時間**不是車速——各段的相對長短仍與班表一致 |
| 緊急停止 | 上報 `PATH_BLOCKED`（CRITICAL），車閂鎖成故障、停在原地、不再接單 |
| 障礙物 | 上報 `OBSTACLE_DETECTED`（WARNING），不轉故障 |
| 清除 | 解除閂鎖，恢復接單 |

中心端若下 `command/execute`，車會先回 `command/ack` 再動作——ack 是「收到」，
不是「做完」。

## 六、車怎麼知道路

訂單只給 A/B 點的 id，中心端不規劃路徑。車輛開機時抓一次圖資
（`/map/library/active`），把 id 換成公尺座標；載客班次帶著完整站序，就照著站序
走出折線；空車移動只有兩點，那就是一段直線。

查不到座標的點會**跳過而不是當成原點**——當成 (0,0) 會讓車瞬間飛到圖台角落，
比少一個轉折點難查得多。兩端都湊不出來的訂單不執行，並在事件裡說明原因。

## 七、路線路徑

「車怎麼知道路」那一節講的是**自動**找路：訂單給 A/B 點，車輛沿軌道走最短路。
那是機器猜的——實際要走哪一條、在哪裡轉、繞不繞，只有人知道。

「路線路徑」分頁讓人把每條路線的路徑**畫下來**，車輛照畫的走：

- 點任一線段中央的 **＋**，該處長出一個折線點，線分成兩段
- 拖折線點改變線徑，按右鍵刪除
- **綠色的站點不能拖也不能刪**——那是班表定的停靠順序，路徑只能決定「怎麼從這一站開到下一站」
- 存檔時記下經過哪些方塊（含各自的參照場域範圍），並切成每 5 公尺一個路徑點

畫的結果存在 `data/route-paths.json`，綁定當下那份地圖，不會同步回 GCP。

### 圖台是借來的，不是重畫的

那一頁的圖台就是 syncdrive_t3 前端的 `MapAreaCanvas`——地圖編輯器用的同一支元件，
儀表板與虛擬圍籬也是重用它。所以方塊、站台、號誌、顏色都與地圖編輯器完全一致，
地圖改版也不會走鐘。

代價是它需要 React 與 Tailwind，和控制頁的原生 JS 混不進同一份 bundle，
所以獨立建置到 `public/paths/`，由控制頁用 iframe 掛進來（同源，共用同一組 API）。
`simulator/` 底下的程式**只讀不改** `frontend/`，也不在產品裡加任何頁面。

改了 `web/` 底下的東西要重新建置：

```bash
npm run build:web     # 或 npm run dev:web 邊改邊建
```

### 兩套座標

| 座標 | 用途 |
|------|------|
| 圖面像素 | 圖台上的位置。編輯器只碰這一組 |
| 場域公尺 | 車輛實際用的，`local_pose` 就是這一套 |

兩者**不是單一線性關係**（實測最大誤差 685 公尺）：每個方塊各自對應自己那一段
現場，所以換算一律逐方塊做。換算只寫在伺服器一份（`PUT /api/routes`），瀏覽器
送的是像素——兩邊各寫一份遲早對不起來，而對不起來的後果是車輛開到別的地方去。

折線點拖到所有方塊之外時沒有對應的場域座標，該點會**標紅且擋下儲存**。

## 八、檔案

| 檔案 | 內容 |
|------|------|
| `server.js` | HTTP 控制面與靜態頁 |
| `src/targets.js` | 連線目標（GCP／本地／自訂） |
| `src/credentials.js` | `.env` 讀取；只對外暴露「有沒有」，不暴露值 |
| `src/apiClient.js` | 對外（3100＋金鑰）與內部（80＋帳密）兩條 HTTP 通道 |
| `src/mapSource.js` | 圖資 → 點位座標 |
| `src/vehicle.js` | 一台車的完整生命週期 |
| `src/fleet.js` | 車隊管理與事件匯流 |
| `src/mapGeometry.js` | 方塊幾何、像素↔公尺逐方塊換算、路徑取樣 |
| `src/routePaths.js` | 路線路徑的儲存與描述 |
| `public/` | 控制頁（原生 JS） |
| `web/` | 「路線路徑」那一頁（React，重用前端圖台元件） |

## 九、與圖台裡那個模擬控制列的關係

數據監控模組原本有一列模擬控制，已經移除。那一列操作的是**伺服器上的示範
程序**——要模擬的車卻應該在外面，用對外介面跟系統互動。控制列留在圖台裡，就
會變成系統自己扮演車輛，那樣不管跑得多順都證明不了介接是通的。

圖台的播放與外推資料流沒有動，只是不再從那一頁下指令。
