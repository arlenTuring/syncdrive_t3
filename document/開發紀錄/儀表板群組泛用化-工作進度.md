# 儀表板畫布群組泛用化重構 — 工作進度

> 內部工程進度文件，供跨對話接續使用。不是產品文件，不納入 `deploy/Dockerfile.web` 的發佈清單。

## 任務目標（摘要）

把儀表板現有的「畫布群組」（`CanvasElementProps.isGroup`）從只支援單一資料來源＋單一樣板＋固定格數輪播，擴充成：

- 多資料來源合併候選項目
- 有效性規則（開始／結束／狀態／到期）
- 優先程度規則（可設定，非寫死）
- 多樣板＋條件式樣板選擇
- 有限格位、優先搶占、候補回補
- 共用格位池的向上翻頁 / 淡入淡出轉場，數值更新不觸發翻頁

完成泛用元件後，**必須**把目前即時數據儀表板實際在用的「正線班次」「整備班表」兩個群組遷移過去、接上真實資料（DB／MQTT），不是留假資料展示。不部署 GCP。

### 真實資料流（背景 agent 已查完，結論如下）

**`demoSql.ts` 名字叫 demo，內容是真的、正在跑的 SQL。** `MAINLINE_SHIFTS_SQL`／`MAINTENANCE_SHIFTS_SQL` 查真實後端表（`operation_orders`／`operation_routes`／`operation_route_stations`／`order_action_states`／`vehicles`；`operation_shifts`），而且 SQL 裡已經有處理過殭屍訂單（同車多筆 PROCESSING 只留真的在跑那筆）、JSON 展開時間軸等業務邏輯。**`utils/resolveBuiltinGroupSql.ts` 是另一個目前寫死 `label` 判斷的地方**（`'正線班次'`→`MAINLINE_SHIFTS_SQL`、`'整備班表'`→`MAINTENANCE_SHIFTS_SQL`、`'車輛狀態'`→`VEHICLE_STATUS_ROW_SQL`），跟 `GroupCanvasRenderer.tsx` 的 `isShiftRosterGroup` 是同一類要拔的分支——**遷移策略＝把這條 SQL 原封不動搬進該群組自己的 `genericGroup.sources[].sqlQuery`，不重寫 SQL 內容，只是把「注入時機」從平台寫死改成群組自己的設定**。

**正線／整備的「有效性」策略不同，不能合併成一種：**
- 正線：SQL 本身已經用真實回報時間判斷殭屍單，回來的列本來就是「目前有效」的——群組層級不需要再猜、不能假設「計畫時間到＝結束」。
- 整備：SQL 用 wall-clock 對 `plannedEndMinute` 硬性截斷，時間到就不會再回來。

→ 這代表 Phase 4 遷移時，`validityRules` 可以很精簡（信任 SQL 回傳的列本身就是有效集合），這次泛用群組的重點反而是**優先程度（正線優先於整備）＋樣板選擇（依來源分流）＋容量池**，不是複雜的有效性判斷。

**MQTT 現況：**
- 正式在用的是 `useShiftFleetMqttMap`／`useShiftVehicleOperationMqtt`（`context/VehicleFleetMqttContext.tsx` → `useVehicleFleetMqttHub`），topic `v1/vtms/{vehicle_code}/operation/update`。
- `hooks/useShiftFleetOperationMqtt.ts` 已標 `@deprecated`，未被 `GroupCanvasRenderer.tsx` 使用，遷移時當死碼忽略。
- **正線**：MQTT 用來即時補進度/ETA/狀態，`mergeOperationMqttShiftRow` 依 `order_id`→`vehicle_code` 順位比對，用 `emittedLive` 防止同一台車的 MQTT 被算成兩張卡（「同一任務不當兩張卡」的既有機制，遷移要保留）。
- **整備**：`mergeMaintenanceShiftRoster` 刻意忽略 MQTT（純 SQL 每 10 秒重算進度），因為整備卡是「部署班表時間軸」的呈現，MQTT 只是執行回報，不該拿來新增/移除/改標整備卡。

**`mainlineTaskModel.ts` / `maintenanceTaskModel.ts`**：`enrichMainlineShiftFields`／`enrichMaintenanceShiftFields` 是純呈現層欄位推導（狀態標籤/顏色/進度），不含到期判斷——到期判斷都在 SQL。`maintTypeLabelColor` 目前是死分支（永遠回同一色），遷移時可以順手用泛用優先程度／樣板條件規則取代。

**儲存機制（重要，Phase 4 要小心）**：Dashboard planes 存後端 `dashboard_planes` 表，REST `GET/PUT {backend}/syncdrive-api/dashboard/planes`。**`PUT` 是整批覆蓋語意**——「送進去的清單就是完整結果，沒出現的會被刪除」。改真實儀表板時絕對不能只 PUT 單一 plane，必須先 GET 全部、只改目標 plane、整批 PUT 回去，而且要先備份（§10.6 要求的「保存可還原版本」）。

**PropertiesPanel.tsx 既有插入點**：`groupRepeatMode==='slots'` 的既有設定區塊在 1710-1793 行左右（`slotCount`/`slotKeyField`/`groupSlotAssignment`/`groupTransition`），是新增「資料來源/優先程度/樣板」區塊的插入點。**既有慣例是把子功能拆成獨立元件**（`components/DualCanvasSettings.tsx`，147 行，掛載兩處：元件已選取時＋子畫布編輯側欄），Phase 3 應該照這個慣例做 `GroupSourcesSettings`/`GroupPrioritySettings`/`GroupTemplatesSettings`，不要全部塞進已經 3400 行的 `PropertiesPanel.tsx` 本體。

**template 存讀既有缺口**：`exportTemplate.ts` 的 `collectFromPlane` 只走 `children`，沒走 `childrenDefault`/`childrenNormal`/`childrenTabN`；`importTemplate.ts` 的 `clonePlaneWithNewIds` 有處理 `children`/`childrenDefault`/`childrenNormal`，但沒有 `childrenTabN`。**這是既有的缺口，不是我造成的**，但 Phase 4 新增 `genericGroup.templates[].children` 時兩邊都要補上遍歷，不能重蹈覆轍。

## 編輯器 UX 修正：多樣板群組的子畫布編輯入口統一（使用者實測回饋）

使用者在畫面上實測發現：泛用群組有多套樣板時，屬性面板頂部「編輯子畫布範本」跟每套樣板各自的「編輯內容」按鈕同時存在，兩個入口語意重複，而且從頂部按鈕進去只會落在第一套樣板，不知道下面還有其他套可以編輯。

**修法**：只留一個入口。

- `PropertiesPanel.tsx` 的 `CanvasSettings`：泛用群組（`genericGroup.enabled`）時，頂部「編輯子畫布範本」按鈕改呼叫 `onEnterTemplateEditMode(defaultTemplateId)`（優先選 `isDefault` 的樣板，沒有就選第一套），不再呼叫舊版 `onEnterEditGroupMode`（那個是操作 `element.children`，跟樣板系統是兩條不相干的資料）。非泛用群組維持原行為不變。
