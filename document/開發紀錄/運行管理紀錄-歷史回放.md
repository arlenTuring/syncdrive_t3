# 運行管理紀錄：歷史回放與逐幀操作

「載具管理模組 → 運行管理紀錄」可以依時間區間或班次唯一碼，回放保存下來的運行歷史。歷史降級播放器也改用同一套游標、逐幀、控制列與車輛資料面板。

整個功能只讀，不會：

- 改營運時鐘
- 送 MQTT
- 控制車輛
- 更新訂單
- 把歷史資料注入即時 Hub

本次沒有新增車端 Topic、payload 欄位或狀態碼。

## 1. 歷史來源與完整度

新表 `vehicle_history_frames` 保存所有歷史。每一筆有這些欄位：

- `seq`：bigserial，前後端一律以字串傳遞
- `stream`
- `stream_key`：狀態來源
- `vehicle_code`
- `topic`
- `order_id`
- `received_at`：後端收到時刻
- `operating_at`：營運時間
- `clock_run`：營運時鐘輪次
- `vehicle_ts`：車端 timestamp
- `source`：`mqtt`、`db` 或 `system`
- `payload`：原始內容
- `derived`：後端衍生資料，與原始內容分開存放

| 串流 | 來源 | 保存規則 | 完整度 |
|---|---|---|---|
| telemetry | MQTT `telemetry/update` | 逐筆保存原始內容，取自正規化之前的複本。後端判位結果存在 `derived.location`。即時系統拒收的舊資料或重送也保存，並標 `derived.rejected`。 | 逐筆 |
| operation | MQTT `operation/update` | 同上 | 逐筆 |
| health | MQTT `health/heartbeat` | 除 timestamp 以外的內容有任何變化就保存。內容沒變時每 10 秒保存一筆，這是降頻，畫面上有標示。 | 內容變更完整 |
| event | MQTT `event/report` | 逐筆 | 逐筆 |
| command_ack | MQTT `command/ack` | 逐筆 | 逐筆 |
| facility | 月台門、場站設施 Topic | 逐筆 | 逐筆 |
| order | `operation_orders` 觸發器 | 快照欄位（狀態、站序、實際開始與結束等）變了才記一筆。每秒都在變的 `current_leg` 不在快照裡，它已經在 operation 原始訊息中。 | 變更完整 |
| order_action | `order_action_states` 觸發器 | 狀態、實際開始或結束、備註變了才記 | 變更完整 |
| order_route | 降級錄製 | 降級期間各訂單的站序 | 降級期間 |
| map / model / clock | 系統 | 地圖內容雜湊、車輛模型快照、營運時鐘輪次。啟動時記一次，之後每 30 秒檢查，有變更才記。 | 變更完整 |

另外三張表記錄錄製本身的狀況：

- **`vehicle_history_segments`**：錄製區段。後端正常停止時區段標 `closed`；異常中斷時，下次啟動會把它標成 `interrupted`。
- **`vehicle_history_gaps`**：區段內的缺段，分兩種：
  - `write_failed`：重試 3 次仍寫不進去
  - `backpressure`：緩衝滿 50,000 筆，暫停收資料
- **`vehicle_history_stream_keys`**：每個狀態來源第一筆和最後一筆的時刻，用來加速起點快照與車輛清單。

缺口在畫面上的呈現：

- **功能上線前的期間**：沒有任何區段，顯示「未錄製」，不會拿目前狀態或班表推算。
- **兩個區段之間**：顯示「後端重啟／停止」。

寫入方式是批次寫入：每 500 ms 一次、每批 500 筆，失敗退避重試。後端關閉時（`enableShutdownHooks`）最多花 10 秒把緩衝寫完，寫不完的部分記成缺段。

事件與指令另外讀既有的 `security_event_logs` 和 `command_logs`。若指令的回應時刻晚於游標，畫面一律顯示「尚未回應」。

## 2. 班次唯一碼

格式：

```
班次唯一碼 = 訂單號 ＋ "@" ＋ operation_orders.created_at（Unix ms）
例：261015-E021830@1791000900000
```

不能單用訂單號，因為資料重置後訂單號可能重複使用，`trip_code` 也每天重複。加上建立時刻，才能精確對到「那一次執行」。

- **顯示位置**：「班次運行紀錄 → 運行紀錄」視窗，時間列下方。後端由 `GET /order/detail` 回傳 `run_code`。
- **複製**：複製的一定是完整值。只有成功才顯示「班次唯一碼已複製」，失敗會說明失敗。
- **貼到回放頁**：後端在現有訂單主檔與歷史中的訂單紀錄裡找這次執行。只輸入訂單號、又對到多次執行時，畫面會列出完整碼讓使用者選。

回放頁對班次的狀態判斷：

| 狀態 | 意思 |
|---|---|
| 查無 | 找不到這個班次 |
| 多筆 | 這個訂單號對到多次執行，需要用完整碼 |
| 尚未執行 | PENDING。不以計畫時間假造軌跡 |
| 無歷史 | 找不到這次執行的資料 |
| 執行中 | 只載入目前已保存的部分 |
| 部分錄製 | 範圍內有缺段或未錄製的區間 |
| 已完整錄製 | 範圍內沒有缺口 |

回放範圍優先用車端回報的實際開始與結束。缺少的那一端，改用這次執行的第一筆或最後一筆營運回報，畫面上會寫明採用的依據。

## 3. 一幀的定義

- **一幀**＝一筆保存紀錄，依「回放時間 t ＋ seq」排序。
  - 一般回放的 t 是後端收到時間。
  - 歷史降級的 t 是營運時間。
- **游標** `{t, seq}`：游標的狀態包含所有不晚於 `(t, seq)` 的資料。
  - `seq = null` 表示整個毫秒都已套用，用於連續播放與拖曳。
- **上一幀／下一幀**：
  - 會自動暫停，畫面不補間。
  - 同一毫秒的多筆可以一筆一筆看。
  - 地圖、任務、資料面板共用同一個游標。
  - 不會越界；跨頁時向後端要相鄰那一筆，不會跳筆。
  - 上一幀是從起點快照重新套用到該筆，不做反向推算。
- **起點快照**：每個狀態來源取不晚於游標的最後一筆，不含任何未來資料。
- **畫面顯示**：目前這一幀的來源（串流、車號、MQTT 收到／資料庫變更／系統紀錄）、seq，以及它是同一毫秒的第幾筆。

## 4. API

運行管理紀錄採「固定調查載具」模式。一般回放 API 都在 `/syncdrive-api/vehicle-history` 底下，權限 `vehicle.log.view`，不需要降級操作權限。

調查用的 API 都必須帶 `vehicle_id`（`vehicles.id`，穩定識別）。後端每次重新驗證並換成通訊代號，不接受名稱或代號直接關聯。停用的車仍可調查。

| API | 參數 | 說明 |
|---|---|---|
| `GET vehicles` | — | 可調查載具：已註冊的全部，含停用，附歷史起訖 |
| `GET resolve/range` | `vehicle_id`、`from`、`to`、`tz` | 時間必須帶時區，一次最多 12 小時。回傳 `vehicle` 與 `vehicle_records`（該車範圍內自己的紀錄數） |
| `GET resolve/shift` | `code`，可選 `vehicle_id` | 解析該次執行實際涉及的車（依紀錄當時的車號），結果見下方 |
| `GET snapshot` | `vehicle_id`、`scope`、`at`、`seq` | 起點快照 |
| `GET frames` | `vehicle_id`、`scope`、`from`、`to`、`after_t`、`after_seq`、`limit` | 先依範圍篩選，再套筆數上限 |
| `GET neighbor` | `vehicle_id`、`at`、`seq`、`dir`、`min`、`max` | 只走調查載具自己的紀錄 |
| `GET vehicle-events` | `vehicle_id`、`from`、`to` | 事件與指令紀錄 |
| `GET map` | `hash` | 地圖快照，不變 |

`resolve/shift` 的結果：

- 只涉及一台車：直接固定為調查載具。
- 涉及多台車：回傳 `multi_vehicle` 與候選清單，使用者選定後帶 `vehicle_id` 再查一次。

`scope` 決定資料範圍：

- **`vehicle`**：逐幀序列。包含該車自己的遙測、營運、健康、事件、指令回應，以及紀錄當時就歸屬它的訂單與站點動作變更。
  - 起點快照另外附上地圖、模型、營運時鐘參照，只作為狀態基準，不算收到的紀錄。
- **`background`**：調查載具以外的一切，包括其他車、場站設施與地圖參照。只用於地圖背景，不進入逐幀序列。

新增索引 `IDX_VEHICLE_HISTORY_VEHICLE_TIME (vehicle_code, received_at, seq)`，已加在同一支 migration 中。

歷史降級播放器維持原本的全系統逐幀與面板切車，API 不變。

## 5. 容量估算

以本機實測的平均列大小計算（含 tuple，未含索引）：

| 串流 | 每列 | 每台每小時 |
|---|---|---|
| telemetry 1 Hz | ≈1.0 KB | 3,600 列，≈3.7 MB |
| operation 1 Hz | ≈0.86 KB | 3,600 列，≈3.1 MB |
| health | ≈0.52 KB | 內容不變時約 360 列，≈0.2 MB；最多 3,600 列，≈1.9 MB |
| 索引 | 每列約 150–180 B | 5 個 btree，≈1.2–1.4 MB |
| 合計 | | **≈8.5 MB／台／小時**（health 每秒都變時約 10 MB） |

全車隊估算：

- 11 台、每天營運 18 小時：每天約 1.7 GB，每月約 50 GB。
- 全天 24 小時：每天約 2.2 GB。
- WAL 與備份量約同等增加。

**保存期限**：本次不做自動刪除，也不承諾永久保存。正式上線前需要決定保存期限，可以選擇：

- 依月份分割資料表
- 定期封存後刪除

在那之前要監控磁碟用量。需要立即停止錄製時，設定 `VEHICLE_HISTORY_RECORDING=0` 並重啟後端，已保存的資料不受影響。

**索引成本**：每筆寫入要維護 5 個 btree 索引，約佔資料量的 18–20%。批次寫入降低了單筆成本。

## 6. 部署

1. 先備份資料庫。
2. 在 VM 上執行 migration。它可以重複執行，只新增資料表、索引、觸發器，以及 `degraded_replay_sessions.frames_source` 欄位：

   ```bash
   sudo docker exec -i syncdrive_postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backend/src/database/migrations/20261015-vehicle-run-history.sql
   ```

   **必須先套 migration 再部署新版。** 正式環境不自動建表；新版的降級查詢會讀 `frames_source` 欄位，欄位不存在會出錯。

3. 依既有流程部署 backend 與 frontend。錄製預設開啟，不需要新增 port 或 Topic。
4. 驗收：
   - 確認 `vehicle_history_segments` 有一筆 `recording`。
   - 確認 `vehicle_history_frames` 有 map、model、clock 三筆系統紀錄。

## 7. 回復

| 想做的事 | 步驟 |
|---|---|
| 只停止錄製 | 設定 `VEHICLE_HISTORY_RECORDING=0` 後重啟。資料保留；降級錄製改回自己保存。 |
| 回復程式 | 回退本次 commit。舊版不讀新表，新表與觸發器留著不影響舊版；觸發器仍會持續寫入，可依需要移除（下一列）。 |
| 移除觸發器 | `DROP TRIGGER vehicle_history_order_change ON operation_orders; DROP TRIGGER vehicle_history_order_action_change ON order_action_states;` |
| 移除資料表 | 確認不再需要歷史後才執行。不可逆：本功能上線後錄的歷史會全部消失；`frames_source='history'` 的降級紀錄也會讀不到回放資料。 |

## 8. 限制

- **功能上線前的期間**：沒有歷史，顯示「未錄製」。最新快照無法補回過去。
- **舊的降級紀錄**（`frames_source='degraded'`）：照舊讀降級自己保存的資料。
- **沒有錄到當時地圖版本的期間**：暫用目前啟用的地圖，畫面上有標示。
- **事件與指令清單**：來自既有紀錄表。若既有流程沒有收進 `security_event_logs`，清單中就不會有；但 MQTT 原始事件仍會出現在「最近事件」。
