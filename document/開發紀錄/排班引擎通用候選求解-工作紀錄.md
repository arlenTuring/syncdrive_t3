# 排班引擎通用候選求解——工作紀錄

> 跨 context 接續用。每階段完成後更新「進度」與「剩餘工作」。只在本地開發驗證，不部署。

## 目標

排班引擎依目前輸入自動產生滿足限制、可實際執行的班表。所有時刻、設施選擇、調整量與受影響班次
都由輸入條件與衝突計算得出；正式程式不得依班次名稱、車列號、站點／設施名稱、日期、時刻、
模板 ID、車輛數、班次數或歷史案例寫特殊分支。

## 前一輪留下、本輪必須清掉的案例常數

| 位置 | 問題 | 處理 |
|---|---|---|
| `generate.ts` 出廠整串後移 `extra <= 120` | 搜尋範圍是看案例定的 | 改由「下一個可吸收空檔」與資源釋放邊界產生候選 |
| `generate.ts` 站位重疊後車延後 `[0,30,60,90,120,180,240]` | 同上 | 改由前車保護結束、後車合法最晚時刻等邊界產生 |
| `delaySameRowChain()` | 會吃掉必要恢復／換線時間 | 只吸收「空檔 − 必要間隔」的真正餘裕 |
| 站位重疊候選前先刪除全場讓站卡 | 局部修復牽動整場 | 只重建受影響車列 |

## 分類：原始設定／可求解變數／衍生結果

**原始設定（求解器唯讀）**：路線站序與各站停靠秒數、停靠模式（`stationDwells`）、路線
`dwellSlackSeconds`、最快／平均行駛與站間 leg、班距時段與屬性、碰撞保護、最低恢復、換線緩衝、
路線關聯圖（允許的接續）、整備任務需求與設施資格／容量、模板任務時窗。

**可求解變數**：未鎖定班次在合法視窗內的發車時刻、合法行駛範圍內的逐站時間配置、設施格與
等待位置、移動路徑與時刻、已允許的備用路線、生成班次的**系統增加緩衝**。

**衍生結果**：逐站到發時刻、站位／設施／轉折點佔用、移動卡、暫停卡、問題清單。

重新生成一律從原始設定起算；系統增加量另存欄位，不寫回原始設定、不累加。

## 已決事項（2026-09-26 使用者確認）

1. **鎖定班次／固定時刻**：不做。使用者不會指定鎖定班次，資料模型也不新增欄位。
   「不越權改動」只針對模板與整備任務本身的時窗規則。
2. **本地模擬器驗收**：用姊妹 repo `../syncdrive_t3_simulator` 的「整日班表重播」模式
   （`src/planReplay.js`：讀後端 `dispatch/plan` 部署中的班表，自己建單、倍速執行），跑完用
   `npm run audit:schedule -- --records` 彙總延誤與原因。需要本地後端＋資料庫；模擬器 repo 不改。
3. **運算預算**：不設時間上限，只設候選數與聯動深度上限；用盡要記錄並揭露「搜尋未完成」。

## 階段計畫

### 階段 1：整理設定、共用限制與回歸資料
- 本文件的設定分類落到型別與程式註解；清點所有會改時刻／位置的策略，標出它們讀哪份限制。
- 共用限制模組：車輛活動區間（執行／行駛／停靠／等待）、站位佔用與保護、設施實際佔用／離格／交接、
  轉折點經過時刻、恢復與換線、固定時刻與逐站下限。驗證器與求解器共用。
- 區分「車最早可移動時刻」與「別車最早可進入時刻」：零秒起終站補的最小佔用只用於碰撞判定，
  不當成車必須等待的命令。
- 回歸工具進 repo：`frontend/scripts/replay-schedule-engine.mts` 輸出安全衝突、必要移動、班次、
  未承接、整備完成與運算時間；歷史 log 不在版控，測試找不到就略過。

### 階段 2：通用候選生成、資源邊界與聯動回溯
- 衝突模型：資源、牽涉的班次／移動／等待、各自合法時窗、可動／固定、影響範圍。
- 候選產生器（全部由邊界推導）：提早抵達讓站、提早進廠、暫停放後返回、延後抵達（需有合法行駛或
  等待承接）、增加前方停靠緩衝、調整擋路車移動、已允許的備用路線、推移後續未鎖定班次。
  不固定只動後車或出不去的那台；設施候選依成本排序逐一驗證。
- 聯動：候選牽動的資源與前後任務依依賴關係擴展（不固定車數），副本上重建受影響的逐站時間、移動、
  等待、佔用（不沿用過期快取、不重複插卡），完整驗證後採用，失敗整組回滾。有運算預算並記錄是否用盡。
- 統一評估：比對衝突簽章（資源、班次對、嚴重度），不能修一筆生一筆；硬限制都滿足之後，
  依「改動小 > 額外緩衝少 > 不必要移動少 > 服務品質好」排序。
- 最終問題清單依完成後班表重建；結果分「可行／目前未找到（附阻擋條件與搜尋限制）／已證明不可行」。

### 階段 3：緩衝調整與前後端一致
- 前後端 `resolveBlockStationDwellInputs`：站點設定與緩衝分開解析，單班緩衝明確提供就生效，
  區分 `0` 與未設定，不複製或修改基本停靠。
- 生成班次另存系統增加緩衝；影響所有適用站點（不適用的站不加）；取解除衝突的最小有效增加量。

### 階段 4：調整紀錄、報告、定位與保存
- 型別：原始緩衝、系統增加量、原因與關聯資源、受影響站序與站點、調整前後到發時刻。
- 分析報表新增預設可見的「已套用的緩衝調整」清單，區分已套用／建議未套用／仍未解決。
- 班次定位抽成共用函式（沿用支援畫面外卡片的流程），報表點擊定位、高亮、顯示明細；目標失效要提示。
- 發布指紋納入停靠與緩衝資料；保存、重開、Undo／Redo、後端輸出一致。

### 階段 5：泛用性測試、建置與本地驗收
- 重新命名、整體平移、換時段與班距、改車輛／設施數、改路線長度、第一設施不可用、多站緩衝、
  模板固定任務不被越權改動、跨午夜與同站重複、重跑穩定、保存重開 Undo／Redo、資源不足或預算用盡。
- 完整建置（前後端）、本地部署生成班表後以模擬器整日重播驗收、瀏覽器檢查報表與定位。
