## 一、先確認你拿到了什麼

介接前你手上應該有三樣東西。缺任何一樣請向我方索取：

| 項目 | 形式 | 範例 |
|------|------|------|
| **Base URL** | 主機位址 ＋ 埠 | `http://34.80.84.224:3100` |
| **API 金鑰** | 一串十六進位字串 | `7b6f…a6` |
| **線上 Swagger** | 網址 | `<Base URL>/api/docs/public` |

另有一份離線規格檔 `openapi.public.json`，可直接匯入 Postman 或用來產生 client，
不需要連到我方主機。

> **這個埠只有對外介面。**同一台主機上還有我方內部系統，但那些端點在這個埠上
> 一律回 `404`——不是權限不足，是**不存在**。你在 Swagger 上看到的四支就是全部。

## 二、認證

所有請求都要帶 `X-API-Key` 標頭。

```bash
curl -H "X-API-Key: <你的金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/operation-shift/timetable/trips"
```

沒帶或帶錯一律回 `401`。金鑰是**單一對外契約**，對所有取用方相同；請勿寫進
前端頁面或公開的程式碼庫。

Swagger 頁面右上角的 **Authorize** 按鈕可以填入金鑰，之後在頁面上直接
「Try it out」就會帶上。

## 三、四支介面在做什麼

分成兩組，**資料來源不同，不互相取代**：

| | 計畫值 | 即時值 |
|---|-------|-------|
| 來源 | 已發布的營運班表 | 車端每秒回報 |
| 車輛識別 | **無** | **有**（`vehicle_code`） |
| 可用條件 | 班表已發布 | 車輛正在回報 |
| 用途 | 時刻表公告、營運規劃 | 現場顯示、到站提示 |

| 介面 | 用途 | 建議輪詢 |
|------|------|---------|
| `GET /syncdrive-api/operation-shift/timetable/trips` | 全部班次與逐站計畫時刻 | 班表更新時才取 |
| `GET /syncdrive-api/operation-shift/timetable/station-etas` | 站點計畫事件流（依站索引） | 同上 |
| `GET /syncdrive-api/vehicles/eta/by-station` | 各站接下來會到的車 | **60 秒** |
| `GET /syncdrive-api/vehicles/eta/by-vehicle` | 各車接下來會到的站 | **60 秒** |

即時值兩支提供的是**同一份資料的兩種索引方式**：站端顯示用 `by-station`，
車輛追蹤畫面用 `by-vehicle`。不需要兩支都打。

## 四、三件最容易誤解的事

### 1. 兩組介面的時間表示法不同

| | 欄位型式 | 意義 |
|---|---------|------|
| 計畫值 | `"00:07:40"` ＋ `460` | **當日第幾秒**，不綁日期 |
| 即時值 | `1786842023000` ＋ `"09:00:23"` | **Epoch 毫秒**，真實世界的某一刻 |

計畫值描述的是「班表上排定的時刻」，本身沒有日期；即時值描述的是「現在這一刻」。
**兩者不要互相換算後混用。**

即時值的每一個 `*_at`（權威值）都有成對的 `*_clock`（顯示值）。兩者不一致時
一律以 `*_at` 為準。倒數計時**必須**用 `eta_at`，不要用 `eta_seconds` 自行累加
——那是以車端回報時刻為基準的，不是以你收到回應的時刻為基準。

```
eta_at = observed_at + eta_seconds × 1000     （恆等式）
```

### 2. 失聯是「資料變舊」，不是「資料消失」

車輛停止回報時，本系統**仍然回傳那台車**，只是：

- `data_age_seconds` 持續累加
- 超過 90 秒後 `arrival_state` 轉為 `UNKNOWN`
- `eta_seconds` / `eta_at` / `eta_clock` 三個欄位一併變成 `null`

**請務必檢查 `data_age_seconds` 或 `arrival_state`，不要只看欄位存不存在。**
只判斷「有沒有這台車」會讓失聯的車看起來一切正常。

同理，回應層級的 `meta.data_quality`：

| 值 | 你該做什麼 |
|----|-----------|
| `OK` | 正常顯示 |
| `DEGRADED` | 照常顯示，但對 `UNKNOWN` 的項目標示「資料中斷」 |
| `DOWN` | **必須停止顯示 ETA**，改顯示資料中斷 |

### 3. 停靠點清單一律完整回傳

`by-station` 會列出**全部停靠點**，包含當下沒有任何車駛近的（`etas` 為空陣列）。
這是為了讓站端可以固定版面，不必自己補齊清單。

`station_id` 與名稱的對應、以及 PIDS 站體側別的歸併方式，見
[車輛即時 ETA API 規格書](車輛即時ETA-API.md) §3.4、§3.5。

## 五、狀態欄位怎麼讀

### `arrival_state`（該車相對於**某一個**停靠點的進度）

| 值 | 意義 |
|----|------|
| `EN_ROUTE` | 行駛中，尚未接近 |
| `APPROACHING` | **即將進站**（剩餘 ≤ 60 秒 或 距離 ≤ 200 公尺） |
| `DOCKING` | 進站對位中 |
| `AT_STATION` | 停靠中 |
| `DEPARTED` | 已離站 |
| `UNKNOWN` | 車端資料逾時，或缺少目標站資訊 |

同一台車對不同停靠點會有不同的 `arrival_state`；`vehicle_phase` 則是整車只有一個。
遇到未列出的值請當作 `UNKNOWN` 處理，不要當成錯誤。

### `plan.delay_state`（暫定）

`delay_seconds` ＝ 預計抵達 − 計畫抵達，**正值表示晚於計畫**。這是客觀數值。

`delay_state` 的分級門檻**尚未經營運確認**，現階段請**以 `delay_seconds` 為準**
自行決定顯示門檻，不要把 `delay_state` 當成唯一判斷依據。

## 六、錯誤處理

| 狀態碼 | 情況 | 建議處置 |
|-------|------|---------|
| `200` | 成功（包含空結果） | 正常 |
| `400` | 參數格式錯誤 | 修正參數，回應 body 有 `error` 與 `detail` |
| `401` | 金鑰缺少或錯誤 | 檢查 `X-API-Key` |
| `404` | 指定的車輛／停靠點不存在，或**庫內尚無已發布班表** | 見下方 |
| `503` | 服務降級 | 改顯示資料中斷，稍後重試 |

錯誤回應格式：

```json
{ "error": "INVALID_PARAM", "detail": "limit_per_station 必須為 1 至 10 的整數" }
```

> **班表兩支在「尚未發布任何班表」時回 404**，這不是故障。此時即時 ETA 兩支
> 仍然可用，只是 `plan` 內各欄位為 `null`、`delay_state` 為 `NO_PLAN`。

---

## 七、輪詢與重試

- **建議間隔 60 秒**，最小 10 秒。低於最小間隔可能回 `429`。
- 請求逾時請設 **5 秒**，逾時後重試，退避建議 5→10→30 秒。
- 支援 `Accept-Encoding: gzip`，建議啟用。
- 請使用 `Connection: keep-alive`。
- 雙方時鐘**必須**以 NTP 同步——`eta_at` 是絕對時刻，時鐘偏移會直接反映成錯誤的
  倒數秒數。

---

## 八、測試環境現況（重要）

目前這台是**測試環境**，資料由模擬車隊產生，有兩件事會影響你看到的內容：

1. **整備時段沒有正線車。**車輛在充電或待命時，`next_stops` 會是空陣列、
   `by-station` 各站也會沒有資料。這是正常的，不是介面故障——換個時段再看即可。
2. **`meta.source` 可能是 `draft_fallback`。**表示目前讀到的是草稿班表，時刻僅供
   對接測試，不代表正式營運時刻。正式環境會是 `published`。
