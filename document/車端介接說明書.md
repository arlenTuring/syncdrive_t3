## 一、任務生命週期

營運班表發布後，中心端依班次時刻產生營運訂單，並以 MQTT 通知指定車輛。車端拉取任務內容、執行移動、持續回報狀態，至任務結束。

```
中心端                                      車端
  │
  │  MQTT  v1/vtms/{vehicle_code}/operation/assign
  ├──────────────────────────────────────────▶│  訂單編號
  │                                           │
  │  GET  /order/queryById?id={order_id}      │
  │◀──────────────────────────────────────────┤
  ├──────────────────────────────────────────▶│  站序、各站計畫時刻、起訖點
  │                                           │
  │  PUT  /order/updateOrderProgress/{id}?status=PROCESSING
  │◀──────────────────────────────────────────┤  訂單轉 PROCESSING
  │                                           │
  │  MQTT  telemetry/update                   │  位置、姿態、運動學（≥ 1 Hz）
  │  MQTT  operation/update                   │  任務進度、目標停靠點、ETA（1 Hz）
  │  MQTT  health/heartbeat                   │  子系統健康（1 Hz）
  │◀──────────────────────────────────────────┤
  │                                           │
  │  PUT  /order/updateOrderProgress/{id}?status=END
  │◀──────────────────────────────────────────┤  訂單轉 END
  │                                           │
  │  MQTT  telemetry/update + operation/update│  待命狀態持續回報
  │◀──────────────────────────────────────────┤
```

指派通知不 Retain，應用層不重送。車端須先訂閱，再用 `GET /syncdrive-api/order/active?vehicle_code=PMS99` 對帳；每次重連／換證後重做，平時建議 30 秒一次。完整流程及錯誤表見 [訂單 API 錯誤與對帳](訂單API錯誤與對帳.md)。

## 二、介面總覽

車端與中心端之間有兩條通道，權責不同：**MQTT 負責持續性的狀態流與即時觸發，REST API 負責具契約性質的狀態變更與任務內容取得**。中心端之訂單狀態僅依 REST API 的回應變更，不採信 MQTT 訊息中的狀態欄位。

### 2.1 MQTT 介面

| 介面 | 方向 | 頻率 | 用途 | 規格 |
|------|------|------|------|------|
| `operation/assign` | 中心端 → 車端 | 事件觸發 | 指派任務，僅傳遞訂單編號 | §四.1 |
| `telemetry/update` | 車端 → 中心端 | ≥ 1 Hz | 位置、姿態、運動學、電量 | §四.2 |
| `operation/update` | 車端 → 中心端 | 1 Hz | 任務進度、目標停靠點、ETA | §四.3 |
| `health/heartbeat` | 車端 → 中心端 | 1 Hz | 子系統健康狀態 | §四.4 |
| `command/execute` | 中心端 → 車端 | 事件觸發 | 控制指令 | §四.5 |
| `command/ack` | 車端 → 中心端 | 回應指令 | 指令接收確認 | §四.5 |
| `event/report` | 車端 → 中心端 | 事件觸發 | 異常與特殊事件上報 | §四.6 |

### 2.2 REST API 介面

| 介面 | 方法 | 用途 | 規格 |
|------|:----:|------|------|
| `/syncdrive-api/order/queryById` | `GET` | 依訂單編號取得站序與各站計畫時刻 | §五.1 |
| `/syncdrive-api/order/updateOrderProgress/{id}` | `PUT` | 回報訂單狀態，訂單狀態之唯一權威來源 | §五.2 |
| `/syncdrive-api/order/action/{actionId}` | `PUT` | 回報站點動作執行結果 | §五.3 |

申請存取憑據之端點（`POST /syncdrive-api/auth/token`）載於[介接說明書](協力廠商介接說明書.md) §一。

## 三、訂閱與連線

### 3.1 MQTT 連線

| 項目 | 值 |
|------|-----|
| 位址 | `mqtts://{host}:8883` |
| 傳輸層 | TLS，雙向驗證 |
| 客戶端憑證 | 由 `POST /syncdrive-api/auth/token` 取得 |
| 身分 | 憑證 CN，等於 `vehicle_code` |

連線不帶帳號密碼。broker 以憑證 CN 作為 username，並據此限制發布路徑。

### 3.2 訂閱 Topic

| Topic | 用途 |
|-------|------|
| `v1/vtms/{vehicle_code}/operation/assign` | 任務指派 |
| `v1/vtms/{vehicle_code}/command/execute` | 控制指令 |
| `v1/vtms/all/#` | 全車隊廣播指令 |

### 3.3 發布權限

車端僅可發布至 `v1/vtms/{vehicle_code}/#`。發布至其他路徑將被 broker 拒絕。

## 四、MQTT 介面規格

### 4.1 `operation/assign`（中心端 → 車端）

Topic `v1/vtms/{vehicle_code}/operation/assign`，QoS 1，Retain `false`。

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `vehicle_code` | String | 車輛代號 | 不放入該欄位 |
| `timestamp` | Long | Unix Epoch 毫秒 | 不放入該欄位 |
| `order_id` | String | 訂單編號 | 不放入該欄位 |
| `priority_level` | Int | 優先權，數值越大越高。對照表見[營運任務狀態協議](營運任務狀態協議.md) §二 | 不放入該欄位 |

```json
{
  "vehicle_code": "PMS01",
  "timestamp": 1787850864927,
  "order_id": "260828-ST0115",
  "priority_level": 50
}
```

訊息僅含訂單編號，不含任務內容。任務內容以 §五.1 拉取。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "OperationAssign",
  "type": "object",
  "required": ["vehicle_code", "timestamp", "order_id", "priority_level"],
  "additionalProperties": false,
  "properties": {
    "vehicle_code":   { "type": "string", "pattern": "^PMS[0-9]{2}$" },
    "timestamp":      { "type": "integer" },
    "order_id":       { "type": "string", "pattern": "^[0-9]{6}-.+$" },
    "priority_level": { "type": "integer", "enum": [100, 90, 50, 40, 30, 20] }
  }
}
```

### 4.3 `operation/update`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/operation/update`，QoS 0，**Retain `true`**。

**頻率**：1 Hz。

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `vehicle_code` | String | 車輛代號 | 不放入該欄位 |
| `timestamp` | Long | Unix Epoch 毫秒 | 不放入該欄位 |
| `vehicle_phase` | String | `AWAITING_DEPARTURE` / `TRANSITING` / `DWELLING` / `DOCKING` / `IDLE` / `FAULTED`。`RUNNING` 與 `TRANSITING` 同義 | 不放入該欄位 |
| `order_status` | String | `PENDING` / `PROCESSING` / `IDLE` / `FAULTED` | 不放入該欄位 |
| `order_id` | String | 訂單編號 | 不放入該欄位 |
| `trip_code` | String | 班次代碼 | 不放入該欄位 |
| `current_leg` | Object | 見下表 | 不放入該欄位 |
| `task_group` | Array | 站點動作執行狀態，見[營運任務狀態協議](營運任務狀態協議.md) §五 | 不放入該欄位 |

`current_leg`

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `target_station_id` | String | 下一個停靠點識別碼，取值見§六.2／[T3 地圖清單](T3地圖站點與路線清單.md) | 不放入該欄位 |
| `distance_to_target_m` | Double | 沿路徑至目標停靠點之距離，公尺 | 不放入該欄位 |
| `eta_seconds` | Int | 至目標停靠點之剩餘秒數 | 不放入該欄位 |

`vehicle_phase`

| 值 | 意義 |
|----|------|
| `AWAITING_DEPARTURE` | 已就位，尚未發車 |
| `TRANSITING`（`RUNNING` 同義） | 行駛中 |
| `DWELLING` | 停靠中 |
| `DOCKING` | 精準對位停靠 |
| `IDLE` | 待命 |
| `FAULTED` | 車輛故障 |

**執行任務時**

```json
{
  "vehicle_code": "PMS02",
  "timestamp": 1787851158019,
  "order_id": "260828-NT0120",
  "trip_code": "NT0120",
  "order_status": "PROCESSING",
  "vehicle_phase": "TRANSITING",
  "current_leg": {
    "target_station_id": "t3_d",
    "distance_to_target_m": 738,
    "eta_seconds": 209
  }
}
```

**待命時**

```json
{
  "vehicle_code": "PMS01",
  "timestamp": 1787851200000,
  "vehicle_phase": "IDLE",
  "order_status": "IDLE"
}
```

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "OperationUpdate",
  "type": "object",
  "properties": {
    "vehicle_code":  { "type": "string" },
    "timestamp":     { "type": "integer" },
    "order_id":      { "type": "string" },
    "trip_code":     { "type": "string" },

    "vehicle_phase": { "type": "string", "enum": ["AWAITING_DEPARTURE", "TRANSITING", "RUNNING", "DWELLING", "DOCKING", "IDLE", "FAULTED"] },

      "type": "object",
```

### 4.4 `health/heartbeat`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/health/heartbeat`，**Retain `true`**，頻率 **1 Hz**，
且於狀態變更時即時推播。

因為本 topic 設 `retain true`，訂閱端一連上就會收到最後一則保留訊息——**不能以
「有沒有收到訊息」判斷車輛是否在線**，失聯判斷一律看訊息內的 `timestamp` 與現在
時刻的差距。逾時門檻由中心端自行設定，不寫在本協議。

欄位定義見[設備健康與異常告警協議](設備健康與異常告警協議.md)。

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `vehicle_code` | String | 車輛代號 | 不放入該欄位 |
| `timestamp` | Long | Unix Epoch 毫秒 | 不放入該欄位 |
| `overall_health` | String | `OK` / `WARNING` / `ERROR` | 不放入該欄位 |
| `subsystems.{name}.status` | String | `OK` / `WARNING` / `ERROR` | 不放入該欄位 |
| `subsystems.{name}.error_codes` | String[] | 錯誤碼，`SCREAMING_SNAKE_CASE` | 不放入該欄位 |

子系統名稱：`COMPUTING`、`SENSING`、`COMMUNICATION`、`CHASSIS`。

```json
{
  "vehicle_code": "PMS01",
  "timestamp": 1787850963347,
  "overall_health": "OK",
  "subsystems": {
    "COMPUTING":     { "status": "OK", "error_codes": [] },
    "SENSING":       { "status": "OK", "error_codes": [] },
    "COMMUNICATION": { "status": "OK", "error_codes": [] },
    "CHASSIS":       { "status": "OK", "error_codes": [] }
  }
}
```

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HealthHeartbeat",
  "type": "object",
  "properties": {
    "vehicle_code":   { "type": "string" },
    "timestamp":      { "type": "integer" },
    "overall_health": { "type": "string", "enum": ["OK", "WARNING", "ERROR"] },
    "subsystems": {
      "type": "object",
      "propertyNames": { "enum": ["COMPUTING", "SENSING", "COMMUNICATION", "CHASSIS"] },
      "additionalProperties": {
        "type": "object",
        "properties": {
          "status":      { "type": "string", "enum": ["OK", "WARNING", "ERROR"] },
          "error_codes": { "type": "array", "items": { "type": "string" } }
        }
      }
    }
  }
}
```

### 4.5 `command/execute` 與 `command/ack`

控制指令由中心端下達至 `v1/vtms/{vehicle_code}/command/execute`；車端於 `v1/vtms/{vehicle_code}/command/ack` 回覆接收確認。指令動作清單見[動態控制與特殊事件協議](動態控制與特殊事件協議.md)。

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `command_id` | String | 指令識別碼，取自 `command/execute` | 不放入該欄位 |
| `vehicle_code` | String | 車輛代號 | 不放入該欄位 |
| `timestamp` | Long | Unix Epoch 毫秒 | 不放入該欄位 |
| `status` | String | `ACCEPTED` / `REJECTED` | 不放入該欄位 |
| `reason` | String | 拒絕原因 | 不放入該欄位 |

`ack` 表示指令已接收，非執行完成。執行結果以 `operation/update` 與 `event/report` 表達。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "CommandAck",
  "type": "object",
  "properties": {
    "command_id":   { "type": "string" },
    "vehicle_code": { "type": "string" },
    "timestamp":    { "type": "integer" },
    "status":       { "type": "string", "enum": ["ACCEPTED", "REJECTED"] },
    "reason":       { "type": "string" }
  }
}
```

### 4.6 `event/report`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/event/report`，QoS 1。

| 欄位 | 型別 | 說明 | 無值 |
|------|------|------|------|
| `event_id` | String | 事件識別碼 | 不放入該欄位 |
| `vehicle_code` | String | 車輛代號 | 不放入該欄位 |
| `timestamp` | Long | Unix Epoch 毫秒 | 不放入該欄位 |
| `event_code` | String | 事件代碼，如 `PATH_BLOCKED`、`OBSTACLE_DETECTED` | 不放入該欄位 |
| `severity` | String | `INFO` / `WARNING` / `CRITICAL` | 不放入該欄位 |
| `location` | Object | `lat`、`lng` | 不放入該欄位 |
| `detail` | String | 事件描述 | 不放入該欄位 |
| `command_id` | String | 對應之指令識別碼 | 不放入該欄位 |
| `params` | Object | 附帶參數 | 不放入該欄位 |

`params` 依 `event_code`：

| `event_code` | `params` 內容 |
|--------------|---------------|
| `INTERLOCK_REQ` | `junction_id`、`action`（`LOCK` / `UNLOCK`） |

## 五、REST API 介面規格

### 5.0 `GET /syncdrive-api/order/active?vehicle_code=PMS99`

取得授權車輛所有 PENDING、PROCESSING、FAULTED 訂單。回應 `{vehicle_code, items}`；items 的每筆內容同 5.1。無訂單回 200、空陣列；有訂單時依建立時間遞增。用於首次連線、重連、換證與週期性對帳。依 id 去重，勿將 PROCESSING 自動重跑。

**參數**

**回應 200**

### 5.2 `PUT /syncdrive-api/order/updateOrderProgress/{id}`

**參數**

| 名稱 | 位置 | 型別 | 說明 | 無值 |
|------|------|------|------|------|
| `id` | Path | String | 訂單編號 | 不放入該欄位 |
| `status` | Query | String | `PROCESSING` / `END` / `FAULTED` | 不放入該欄位 |

**狀態轉移**

| 現況 | 允許轉移至 |
|------|-----------|
| `PENDING` | `PROCESSING`、`FAULTED` |
| `PROCESSING` | `END`、`FAULTED` |
| `FAULTED` | `PROCESSING`、`END` |
| `END` | 無 |

不允許之轉移回應 `400`。

本端點為訂單狀態之唯一權威來源。中心端之訂單狀態僅依本端點的 HTTP 成功回應變更，不採信 MQTT 訊息中的狀態欄位。

**值域只有三個，不會擴充。**本端點是**訂單進度**回報，不是事件通知：`END` 表示
這張訂單的營運契約已了結，`FAULTED` 是**所有非正常結束情形的收納值**（拒絕、失敗、
無法到達、中止、取消等）。車端若有更細的結束分類，那是自動化層的語意，與營運層
的訂單契約狀態不是同一件事，**請走 `event/report` 上報，不要往這裡塞新的狀態值**。
結束原因碼的擺放位置另案討論。

```bash
curl -X PUT -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/order/updateOrderProgress/260828-ST0115?status=PROCESSING"
```

### 5.3 `PUT /syncdrive-api/order/action/{actionId}`

回報站點動作（語音、開關門等）之執行結果。動作代碼與觸發時機見[營運任務狀態協議](營運任務狀態協議.md) §六.1。

本端點亦為**逐案回報**的通用機制：當營運端需要看到某個車端內部流程的進度時，
由中心端逐案開立 action，車端做完回報即可，不需將該流程放進 `task_group` 字典。
**要看多細由中心端決定，車端不需要自行擴充任務字典。**

以路口路權為例（實際是否開立這組 action 由營運端決定，目前未定案）：

| 中心端開立的 action | 車端何時回報 `COMPLETED` |
|---|---|
| `INTERLOCK_REQ_SEND_ACT` | 已向號誌系統送出路權請求 |
| `INTERLOCK_REQ_ALLOWED_ACT` | 已收到號誌系統核准 |

車端只需在做完該動作時更新對應的 action，路權的請求與核准過程本身仍由車端與
SCADA 直接完成，中心端不介入控制迴路。

| 名稱 | 位置 | 型別 | 說明 | 無值 |
|------|------|------|------|------|
| `actionId` | Path | String | 動作識別碼 | 不放入該欄位 |
| `status` | Body | String | `PENDING` / `IN_PROGRESS` / `COMPLETED` / `FAILED` | 不放入該欄位 |
| `note` | Body | String | 卡關或失敗之原因 | 不放入該欄位 |
| `actual_start_time` | Body | Long | 實際開始時刻 | 不放入該欄位 |
| `actual_end_time` | Body | Long | 實際結束時刻 | 不放入該欄位 |
