## 一、任務生命週期

營運班表發布後，中心端依班次時刻產生營運訂單，並以 MQTT 通知指定車輛。車端拉取任務內容、執行移動、持續回報狀態，至任務結束。

```
中心端                                      車端
  │
  │  MQTT  v1/vtms/{vehicle_code}/operation/assign
  ├──────────────────────────────────────────▶│  訂單編號
  │                                           │
  │  GET  /order/queryById?id={order_id}      │
  │◀──────────────────────────────────────────┤
  ├──────────────────────────────────────────▶│  站序、各站計畫時刻、起訖點
  │                                           │
  │  PUT  /order/updateOrderProgress/{id}?status=processing
  │◀──────────────────────────────────────────┤  訂單轉 PROCESSING
  │                                           │
  │  MQTT  telemetry/update                   │  位置、姿態、運動學（≥ 1 Hz）
  │  MQTT  operation/update                   │  任務進度、目標停靠點、ETA（1 Hz）
  │  MQTT  health/heartbeat                   │  子系統健康（每 5 秒）
  │◀──────────────────────────────────────────┤
  │                                           │
  │  PUT  /order/updateOrderProgress/{id}?status=end
  │◀──────────────────────────────────────────┤  訂單轉 END
  │                                           │
  │  MQTT  telemetry/update + operation/update│  待命狀態持續回報
  │◀──────────────────────────────────────────┤
```

指派訊息不重送。車端須於連線建立後即維持訂閱狀態。

## 二、訂閱與連線

### 2.1 MQTT 連線

| 項目 | 值 |
|------|-----|
| 位址 | `mqtts://{host}:8883` |
| 傳輸層 | TLS，雙向驗證 |
| 用戶端憑證 | 由 `POST /syncdrive-api/auth/token` 取得 |
| 身分 | 憑證 CN，等於 `vehicle_code` |

連線不帶帳號密碼。broker 以憑證 CN 作為 username，並據此限制發布路徑。

### 2.2 訂閱 Topic

| Topic | 用途 |
|-------|------|
| `v1/vtms/{vehicle_code}/operation/assign` | 任務指派 |
| `v1/vtms/{vehicle_code}/command/execute` | 控制指令 |
| `v1/vtms/all/#` | 全車隊廣播指令 |

### 2.3 發布權限

車端僅可發布至 `v1/vtms/{vehicle_code}/#`。發布至其他路徑將被 broker 拒絕。

## 三、介面規格

### 3.1 `operation/assign`（中心端 → 車端）

Topic `v1/vtms/{vehicle_code}/operation/assign`，QoS 1，Retain `false`。

| 欄位 | 型別 | 說明 |
|------|------|------|
| `vehicle_code` | String | 車輛代號 |
| `timestamp` | Long | Unix Epoch 毫秒 |
| `order_id` | String | 訂單編號 |
| `priority_level` | Int | 優先權，數值越大越高。對照表見[營運任務狀態協議](營運任務狀態協議.md) §二 |

```json
{
  "vehicle_code": "PMS-01",
  "timestamp": 1787850864927,
  "order_id": "260828-ST0115",
  "priority_level": 50
}
```

訊息僅含訂單編號，不含任務內容。任務內容以 §3.2 拉取。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "OperationAssign",
  "type": "object",
  "required": ["vehicle_code", "timestamp", "order_id", "priority_level"],
  "additionalProperties": false,
  "properties": {
    "vehicle_code":   { "type": "string", "pattern": "^PMS-[0-9]{2}$" },
    "timestamp":      { "type": "integer" },
    "order_id":       { "type": "string", "pattern": "^[0-9]{6}-.+$" },
    "priority_level": { "type": "integer", "enum": [100, 90, 50, 40, 30, 20] }
  }
}
```

### 3.2 `GET /syncdrive-api/order/queryById`

**參數**

| 名稱 | 位置 | 型別 | 必填 | 說明 |
|------|------|------|:---:|------|
| `id` | Query | String | ✓ | 訂單編號 |

**回應 200**

| 欄位 | 型別 | 說明 |
|------|------|------|
| `id` | String | 訂單編號 |
| `tripCode` | String | 班次代碼 |
| `routeId` | String \| null | 路線識別碼 |
| `vehicleCode` | String | 車輛代號 |
| `priorityLevel` | Int | 優先權 |
| `status` | String | `PENDING` / `PROCESSING` / `END` / `FAULTED` |
| `lineKind` | String \| null | `MAINLINE`（載客班次）／ `MAINTENANCE`（整備與空車移動） |
| `plannedStart` | String | 計畫起始時刻，Epoch 毫秒，以字串回傳 |
| `plannedEnd` | String | 計畫結束時刻，同上 |
| `payload.kind` | String | `passenger` / `movement` / `maintenance` |
| `payload.route_code` | String \| null | 路線代號 |
| `payload.route_name` | String \| null | 路線名稱 |
| `payload.yard_slot_id` | String | 整備訂單佔用之場區格位代號 |
| `payload.origin` | Object \| null | 起點，含 `id`、`name`、`kind`（`station` / `facility`）、`depart_at` |
| `payload.destination` | Object \| null | 終點，含 `id`、`name`、`kind`（`station` / `facility`）、`arrive_at` |
| `payload.stations[]` | Array | 站序，欄位見下表 |

`payload.stations[]`

| 欄位 | 型別 | 說明 |
|------|------|------|
| `order` | Int | 站序，自 1 起 |
| `station_id` | String | 停靠點或渡線途經點識別碼 |
| `station_name` | String | 名稱 |
| `role` | String | `origin` / `intermediate` / `terminal` |
| `arrive_at` | Long \| null | 計畫抵達時刻。起點為 `null` |
| `depart_at` | Long \| null | 計畫發車時刻。終點為 `null` |
| `dwell_seconds` | Int | 計畫停留秒數 |

```bash
curl -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/order/queryById?id=260828-ST0115"
```

```json
{
  "id": "260828-ST0115",
  "tripCode": "ST0115",
  "vehicleCode": "PMS-01",
  "priorityLevel": 50,
  "status": "PENDING",
  "lineKind": "MAINLINE",
  "plannedStart": "1787850950000",
  "plannedEnd": "1787851130000",
  "payload": {
    "kind": "passenger",
    "route_code": "ST",
    "route_name": "S2W上行>T3上行",
    "origin":      { "id": "station_6", "name": "S2W上行", "kind": "station", "depart_at": 1787850950000 },
    "destination": { "id": "station_4", "name": "T3上行", "kind": "station", "arrive_at": 1787851090000 },
    "stations": [
      { "order": 1, "station_id": "station_6", "station_name": "S2W上行", "role": "origin",      "arrive_at": null,          "depart_at": 1787850950000, "dwell_seconds": 0 },
      { "order": 2, "station_id": "station_4", "station_name": "T3上行",  "role": "terminal",     "arrive_at": 1787851090000, "depart_at": null,          "dwell_seconds": 0 }
    ]
  }
}
```

`stations[]` 之筆數依路線實際站序而定：兩站間若無渡線途經點，僅列出起訖兩筆；若路線經渡線，中間各渡線途經點以 `role: "intermediate"` 逐筆列出。渡線途經點識別碼與座標見§四.3。

中心端不提供路徑。站序與各站計畫時刻為任務內容之全部，路徑由車端依 §四 之場域座標自行規劃。

回應可能含本表未列之欄位（中心端內部記帳用途，或執行中訂單併入之進度欄位），車端應僅讀取本表所列欄位，未列欄位不保證存在或格式穩定。

### 3.3 `PUT /syncdrive-api/order/updateOrderProgress/{id}`

**參數**

| 名稱 | 位置 | 型別 | 必填 | 說明 |
|------|------|------|:---:|------|
| `id` | Path | String | ✓ | 訂單編號 |
| `status` | Query | String | ✓ | `processing` / `end` / `faulted` |

**狀態轉移**

| 現況 | 允許轉移至 |
|------|-----------|
| `PENDING` | `PROCESSING` |
| `PROCESSING` | `END`、`FAULTED` |
| `FAULTED` | `PROCESSING`、`END` |
| `END` | 無 |

不允許之轉移回應 `400`。

本端點為訂單狀態之唯一權威來源。中心端之訂單狀態僅依本端點的 HTTP 成功回應變更，不採信 MQTT 訊息中的狀態欄位。

```bash
curl -X PUT -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/order/updateOrderProgress/260828-ST0115?status=processing"
```

| 名稱 | 位置 | 型別 | 說明 |
|------|------|------|------|
| `actionId` | Path | String | 動作識別碼 |
| `status` | Body | String | `PENDING` / `IN_PROGRESS` / `COMPLETED` / `FAILED` |
| `note` | Body | String | 卡關或失敗之原因 |
| `actual_start_time` | Body | Long | 實際開始時刻 |
| `actual_end_time` | Body | Long | 實際結束時刻 |

### 3.5 `telemetry/update`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/telemetry/update`，QoS 0，Retain `false`。

**頻率**：至少 1 Hz。中心端圖台以相鄰兩筆之間的線性插值繪製車輛移動，兩筆之間的位移應維持在 10 公尺以內；車速較高時須提高頻率，建議上限 10 Hz。

欄位定義見[車輛動態協議](車輛動態協議.md) §三。以下為本介面實際採用之欄位。

| 欄位 | 型別 | 單位 | 說明 |
|------|------|------|------|
| `vehicle_code` | String | | 車輛代號 |
| `timestamp` | Long | ms | Unix Epoch |
| `trip_code` | String | | 執行任務時之班次代碼 |
| `badge_label` | String | | 圖台車輛標示文字，通常同 `trip_code` |
| `global_pose.latitude` | Double | 度 | WGS84 緯度 |
| `global_pose.longitude` | Double | 度 | WGS84 經度 |
| `global_pose.altitude` | Double | m | 海拔 |
| `local_pose.position.x` | Double | m | 場域座標 X |
| `local_pose.position.y` | Double | m | 場域座標 Y |
| `local_pose.position.z` | Double | m | 場域座標 Z |
| `local_pose.orientation.{w,x,y,z}` | Double | | 姿態四元數 |
| `local_pose.heading` | Double | rad | 車頭朝向角，由四元數轉換 |
| `kinematics.velocity` | Double | **km/h** | 縱向行駛速度 |
| `kinematics.acceleration` | Double | m/s² | 加速度，含正負 |
| `kinematics.angular_velocity` | Double | rad/s | 旋轉角速度 |
| `actuation_feedback.throttle` | Double | % | 動力輸出深度 0–100 |

| `actuation_feedback.steering_angle` | Double | rad | 前輪實際轉角 |
| `actuation_feedback.gear` | String | | `P` / `R` / `N` / `D` |

### 3.6 `operation/update`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/operation/update`，QoS 0，**Retain `true`**。

**頻率**：1 Hz。執行任務與待命時均須發布。

| 欄位 | 型別 | 必填 | 說明 |
|------|------|:---:|------|
| `vehicle_code` | String | ✓ | 車輛代號 |
| `timestamp` | Long | ✓ | Unix Epoch 毫秒 |
| `vehicle_phase` | String | ✓ | `AWAITING_DEPARTURE` / `TRANSITING` / `DWELLING` / `DOCKING` / `IDLE` / `FAULTED`。`RUNNING` 為 `TRANSITING` 之相容別名，兩者中心端視為同義 |
| `order_status` | String | | `PENDING` / `PROCESSING` / `IDLE` / `FAULTED` |
| `order_id` | String | 執行任務時 | 訂單編號 |
| `trip_code` | String | | 班次代碼 |
| `line_kind` | String | | `MAINLINE` / `MAINTENANCE` |
| `route_id` | String | | 路線識別碼 |
| `yard_slot_id` | String | | 車輛所在或佔用之場區格位代號 |
| `current_leg` | Object | 執行任務時 | 見下表 |
| `route_progress` | Int | | 任務完成百分比 0–100 |
| `task_group` | Array | | 站點動作執行狀態，見[營運任務狀態協議](營運任務狀態協議.md) §五 |

`current_leg`

| 欄位 | 型別 | 說明 |
|------|------|------|
| `target_station_id` | String | 下一個要抵達的停靠點識別碼 |
| `distance_to_target_m` | Double | 沿路徑至目標停靠點之距離，公尺 |
| `eta_seconds` | Int | 至目標停靠點之剩餘秒數，由車端推算 |
| `leg_eta_max` | Int | 本段（前一停靠點至目標停靠點）之計畫總秒數 |

#### `current_leg` 各欄位的用途

`current_leg` 是中心端將車輛回報對應回營運班表的唯一依據。四個欄位分別支撐不同的下游輸出：

**`target_station_id`** — 中心端以此欄位比對班表中的站序，取得該站的計畫抵達時刻。取值必須是停靠點識別碼（見§四.2，現行為 `station_1`～`station_6`）或渡線途經點（`xo_*`，見§四.3），不可填站體名稱。同一站體含上行與下行兩個獨立的停靠點，填站體名稱無法區分方向，將導致比對失敗。

此欄位缺漏時，該車在到站預測介面 `GET /vehicles/eta/by-vehicle` 的 `next_stop` 為 `null`，站端顯示無資料，誤點統計亦無法計算。

**`eta_seconds`** — 至目標停靠點的剩餘秒數，非整趟任務的剩餘秒數。中心端據此判定 `arrival_state`：`eta_seconds ≤ 60` 或 `distance_to_target_m ≤ 200` 時標記為即將進站。填入整趟剩餘秒數將使中途各站均不觸發即將進站狀態。

中心端不重算此值，原值透傳至到站預測介面。

**`distance_to_target_m`** — 沿規劃路徑之距離，非直線距離。與 `eta_seconds` 共同構成即將進站的判定條件。

**`leg_eta_max`** — 本段的計畫總秒數，中心端以此為分母計算段落剩餘百分比。取值為前一停靠點的計畫發車時刻至目標停靠點的計畫抵達時刻之差。此欄位缺漏時，中心端改以「已觀察到的最大 `eta_seconds`」為分母，各段進度將自 0% 起跳。

#### `vehicle_phase` 各值的用途

| 值 | 意義 | 對訂單狀態的影響 |
|----|------|----------------|
| `AWAITING_DEPARTURE` | 已就位，尚未發車 | 訂單維持 `PENDING` |
| `TRANSITING`（相容別名 `RUNNING`） | 行駛中 | 訂單由 `PENDING` 轉 `PROCESSING` |
| `DWELLING` | 停靠中（含上下客） | 同上 |
| `DOCKING` | 精準對位停靠 | 同上 |
| `IDLE` | 待命，未執行任務 | 不影響訂單狀態；用於場區定位 |
| `FAULTED` | 車輛故障 | 訂單標記異常，見§3.3 狀態轉移 |

中心端僅依 `TRANSITING`／`DWELLING`／`DOCKING` 之任一值，將對應訂單自 `PENDING` 轉為 `PROCESSING`；訂單狀態之正式權威仍以 `PUT /order/updateOrderProgress/{id}` 為準（見§3.3），本欄位僅供中心端提前感知。

**執行任務時**

```json
{
  "vehicle_code": "PMS-02",
```

任務結束後仍須持續發布 `telemetry/update` 與 `operation/update`。停止發布時，中心端圖台將沿用最後一次回報的位置。

### 3.7 `health/heartbeat`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/health/heartbeat`，**Retain `true`**，頻率 1 Hz。

欄位定義見[設備健康與異常告警協議](設備健康與異常告警協議.md)。

| 欄位 | 型別 | 說明 |
|------|------|------|
| `vehicle_code` | String | 車輛代號 |
| `timestamp` | Long | Unix Epoch 毫秒 |
| `overall_health` | String | `OK` / `WARNING` / `ERROR`。車端僅回報此三值；`OFFLINE` 為中心端於心跳逾時時推導之值，不由車端發送 |
| `subsystems.{name}.status` | String | `OK` / `WARNING` / `ERROR` |
| `subsystems.{name}.error_codes` | String[] | 錯誤碼，`SCREAMING_SNAKE_CASE` |

子系統名稱：`COMPUTING`、`SENSING`、`COMMUNICATION`、`CHASSIS`，四者缺一即整筆捨棄。

```json
{
  "vehicle_code": "PMS-01",
  "timestamp": 1787850963347,
  "overall_health": "OK",
  "subsystems": {
    "COMPUTING":     { "status": "OK", "error_codes": [] },
    "SENSING":       { "status": "OK", "error_codes": [] },
    "COMMUNICATION": { "status": "OK", "error_codes": [] },
    "CHASSIS":       { "status": "OK", "error_codes": [] }
  }
}
```

車端為 `vehicle_phase` 與 `overall_health` 之唯一寫入源。中心端僅聚合與呈現，不覆寫。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HealthHeartbeat",
  "type": "object",
  "required": ["vehicle_code", "timestamp", "overall_health", "subsystems"],
  "properties": {
    "vehicle_code":   { "type": "string" },
    "timestamp":      { "type": "integer" },
    "overall_health": { "type": "string", "enum": ["OK", "WARNING", "ERROR"] },
    "subsystems": {
      "type": "object",
      "required": ["COMPUTING", "SENSING", "COMMUNICATION", "CHASSIS"],
      "propertyNames": { "enum": ["COMPUTING", "SENSING", "COMMUNICATION", "CHASSIS"] },
      "additionalProperties": {
        "type": "object",
        "required": ["status"],
        "properties": {
          "status":      { "type": "string", "enum": ["OK", "WARNING", "ERROR"] },
          "error_codes": { "type": "array", "items": { "type": "string" } }
        }
      }
    }
  }
}
```

### 3.8 `command/execute` 與 `command/ack`

控制指令由中心端下達至 `v1/vtms/{vehicle_code}/command/execute`；車端於 `v1/vtms/{vehicle_code}/command/ack` 回覆接收確認。指令動作清單見[動態控制與特殊事件協議](動態控制與特殊事件協議.md)。

| 欄位 | 型別 | 說明 |
|------|------|------|
| `command_id` | String | 指令識別碼，取自 `command/execute` |
| `vehicle_code` | String | 車輛代號 |
| `timestamp` | Long | Unix Epoch 毫秒 |
| `status` | String | `ACCEPTED` / `REJECTED` |
| `reason` | String | `REJECTED` 時必填 |

`ack` 表示指令已接收，非執行完成。執行結果以 `operation/update` 與 `event/report` 表達。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "CommandAck",
  "type": "object",
  "required": ["command_id", "vehicle_code", "timestamp", "status"],
  "properties": {
    "command_id":   { "type": "string" },
    "vehicle_code": { "type": "string" },
    "timestamp":    { "type": "integer" },
    "status":       { "type": "string", "enum": ["ACCEPTED", "REJECTED"] },
    "reason":       { "type": "string" }
  }
}
```

### 3.9 `event/report`（車端 → 中心端）

Topic `v1/vtms/{vehicle_code}/event/report`，QoS 1。

| 欄位 | 型別 | 說明 |
|------|------|------|
| `event_id` | String | 事件識別碼 |
| `vehicle_code` | String | 車輛代號 |
| `timestamp` | Long | Unix Epoch 毫秒 |
| `event_code` | String | 事件代碼，如 `PATH_BLOCKED`、`OBSTACLE_DETECTED` |
| `severity` | String | `INFO` / `WARNING` / `CRITICAL` |
| `location` | Object | `lat`、`lng` |
| `detail` | String | 事件描述 |
| `command_id` | String | 因指令而起之事件填入對應指令識別碼 |
| `params` | Object | 特定事件碼之附帶參數，見下表 |

`severity` 為 `CRITICAL` 時，車輛進入 `FAULTED`，在人工復歸前不接受新任務。

`params` 之內容依 `event_code` 而定：

| `event_code` | `params` 內容 |
|--------------|---------------|
| `INTERLOCK_REQ` | `junction_id`（路口識別碼）、`action`（`LOCK` / `UNLOCK`） |

未列於上表之事件碼無固定 `params` 結構，可省略此欄位。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "EventReport",
  "type": "object",
  "required": ["event_id", "vehicle_code", "timestamp", "event_code", "severity"],
  "properties": {
    "event_id":     { "type": "string" },
    "vehicle_code": { "type": "string" },
    "timestamp":    { "type": "integer" },
    "event_code":   { "type": "string" },
    "severity":     { "type": "string", "enum": ["INFO", "WARNING", "CRITICAL"] },
    "location": {
      "type": "object",
      "properties": { "lat": { "type": "number" }, "lng": { "type": "number" } }
    },
    "detail":     { "type": "string" },
    "command_id": { "type": "string" },
    "params":     { "type": "object" }
  }
}
```

## 四、場域座標

`local_pose.position` 與 `current_leg.distance_to_target_m` 採場域參照座標系，單位公尺，X 軸向東為正，Y 軸向北為正。

地圖物件另有一組圖面排版座標（畫布上的顯示位置），與場域參照座標系分屬不同的仿射變換，數值不可互換、也不可由圖面座標換算得出。下列各表一律為場域參照座標，可直接使用。

### 4.1 已知設施座標範圍

依現行已提供場域座標之設施（停靠點、場區格位）彙總，供估算場域大小；非場域邊界之正式公告值，實際可通行範圍以車端自身地圖為準。

| 軸 | 最小值 (m) | 最大值 (m) |
|----|----------:|----------:|
| X（東西向） | 101.75 | 1050 |
| Y（南北向） | 100 | 333 |

### 4.2 停靠點

`payload.stations[].station_id` 與 `current_leg.target_station_id` 之取值。現行已啟用 6 個停靠點；後續依營運路線擴增時，本表將同步更新。

| `station_id` | 名稱 | X (m) | Y (m) |
|--------------|------|------:|------:|
| `station_1` | N2W上行 | 810 | 105.25 |
| `station_2` | N2W下行 | 840 | 101.75 |
| `station_3` | T3下行 | 101.75 | 170 |
| `station_4` | T3上行 | 105 | 230 |
| `station_5` | S2W下行 | 810 | 305.25 |
| `station_6` | S2W上行 | 840 | 301.75 |

### 4.3 渡線途經點

上下行正線之間如設有轉換點，以 `xo_` 為前綴的識別碼表示，成對出現。現行地圖尚未啟用渡線途經點；`payload.stations[]` 與 `current_leg.target_station_id` 於本階段僅會出現 4.2 之停靠點識別碼。啟用後將於本表補列各途經點之場域座標。
