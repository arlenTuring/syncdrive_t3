# SyncDrive T3 車端介接說明書

| 項目 | 內容 |
|------|------|
| 提供方 | 台智駕 SyncDrive T3 車輛行車管理系統 |
| 版本 | v1.0（2026-08-28） |
| 讀者 | 要把自駕車接上本系統的協力廠商 |
| 通訊方式 | MQTT（雙向、高頻）＋ HTTP/JSON（單向、契約） |

> 這份講的是**車端**——車輛怎麼收任務、怎麼跑、怎麼回報。
> 只需要讀取班表與到站預測、不需要接車的取用方，請看
> [協力廠商介接說明書](協力廠商介接說明書.md)，那份是唯讀的四支 API。

## 一、你要拿到什麼

| 項目 | 形式 | 用途 |
|------|------|------|
| **主機位址** | 例 `34.80.84.224` | MQTT 與對外 API 同一台 |
| **MQTT 帳密** | **每台車一組**，帳號＝車輛代號 | 連 broker |
| **API 金鑰** | 一串十六進位字串 | 對外 REST 的 `x-api-key` |
| **場域圖資** | 一份 JSON 檔 | 站點與軌道的座標 |

四樣缺一不可。圖資是**交付一份檔案**，不是線上端點——車上帶著那份圖跑，
換版時重新收檔，這與真實車廠的作業方式一致。

### 三條通道

```
                        ┌──────────────────────────────┐
   車端                 │      SyncDrive T3 中心端      │
                        └──────────────────────────────┘
    │                                   │
    │  ① MQTT  1883                     │   雙向、高頻、不保證送達
    │     帳號＝vehicle_code             │   位置與進度回報、發車觸發、指令
    │◀─────────────────────────────────▶│
    │                                   │
    │  ② 對外 REST  3100                │   單向、低頻、契約性狀態
    │     x-api-key                      │   拉任務內容、回報訂單狀態
    │──────────────────────────────────▶│
    │                                   │
    │  ③ 場域圖資（檔案，離線）           │   站點與軌道座標
    │◀── － － － － － － － － － － － －   │
```

**3100 埠上只有七支端點，其餘一律 `404`**——不是權限不足，是不存在。
中心端的內部功能在另一個埠，你連不到，也不需要。

| 對外端點 | 車端會用到 |
|---|---|
| `GET /syncdrive-api/order/queryById` | ✅ 拉任務內容 |
| `PUT /syncdrive-api/order/updateOrderProgress/{id}` | ✅ 回報訂單狀態 |
| `PUT /syncdrive-api/order/action/{actionId}` | ✅ 回報站點動作 |
| `GET /syncdrive-api/operation-shift/timetable/trips` | 對照用 |
| `GET /syncdrive-api/operation-shift/timetable/station-etas` | 對照用 |
| `GET /syncdrive-api/vehicles/eta/by-station` | 對照用 |
| `GET /syncdrive-api/vehicles/eta/by-vehicle` | 對照用 |

## 二、從班表發布到車輛移動

這一節回答「班表按下發布之後，到底發生了什麼」。

```
  【人】在營運班表按下「部署」
     │
     ▼
  【中心端】即時調度引擎（每 5 秒檢查一次）
     │   展開今日全部班次 → 挑出「發車前 90 秒內」的
     │   已經下過的不再下（記憶體 ＋ 資料庫兩層防重複）
     ▼
  【中心端】建立訂單，狀態 PENDING
     │   order_id = YYMMDD-trip_code，例 260828-ST0115
     ▼
  【中心端】MQTT  v1/vtms/{車}/operation/assign     ← ①
     │   只帶 order_id，不帶任務內容
     ▼
  【車端】GET /order/queryById?id=…                 ← ②
     │   拿回站序、各站計畫時刻、起訖點
     ▼
  【車端】自行規劃路徑                              ← ③
     │
     ▼
  【車端】PUT …/updateOrderProgress/{id}?status=processing   ← ④
     │   訂單轉 PROCESSING。沒呼叫成功，中心端就當這班還沒發車
     ▼
  【車端】沿途回報（持續）                          ← ⑤
     │   telemetry/update    位置、速度、車頭方向
     │   operation/update    訂單進度、下一站、ETA
     │   health/heartbeat    子系統健康
     ▼
  【車端】PUT …/updateOrderProgress/{id}?status=end  ← ⑥
     │   訂單轉 END
     ▼
  【車端】回到待命，仍持續回報位置                   ← ⑦
```

### 調度引擎的三個參數

| 參數 | 預設 | 意義 |
|------|------|------|
| `DISPATCH_TICK_SECONDS` | `5` | 多久檢查一次有沒有該發的班次 |
| `DISPATCH_LEAD_SECONDS` | `90` | **發車前多久下訂單**。車端要拉任務、規劃路徑、開到起點，都需要時間 |
| `DISPATCH_CATCH_UP_SECONDS` | `300` | 補發窗口。引擎重啟後，發車時刻已過但在這個窗口內的仍補發 |

所以：**`assign` 會在計畫發車時刻的前 90 秒送達**，不是發車當下。
車端收到之後有 90 秒可以準備。

`assign` 不重送。車端在收到的當下如果還沒準備好（圖資沒載入、還沒連上
REST），這一班就漏掉了——所以**先取圖資、再連 MQTT**。

## 三、車端要實作的七個步驟

以下每一步都對應本系統附的模擬器實作。模擬器頁面上「逐車流程」分頁會把這七步
連同實際 JSON 逐筆列出來，可以邊接邊對。

### ① 連上 MQTT broker

```
mqtt://PMS-05:<該車密碼>@34.80.84.224:1883
```

broker 自 2026-08-26 起**關閉匿名連線**。username **必須等於自身
`vehicle_code`**，否則在連線階段就被拒（`Connection Refused: not authorised`），
不是發布時才失敗。

連上之後訂閱兩個 topic：

```
v1/vtms/{vehicle_code}/operation/assign     發車觸發
v1/vtms/{vehicle_code}/command/execute      即時指令
```

要接受全域廣播指令的話，另外訂閱 `v1/vtms/all/#`。

### ② 收到 assign

```json
{
  "vehicle_code": "PMS-01",
  "timestamp": 1787850864927,
  "order_id": "260828-ST0115",
  "priority_level": 50
}
```

**只有 order_id，沒有任務內容。**這是刻意的：MQTT 不保證順序也不保證只送一次，
把整包任務塞在裡面，重送或亂序都會讓車端拿到錯的內容。

`priority_level` 數字越大優先權越高。收到比當前任務更高優先權的指派時，車端
必須有中斷當前行為的能力。對照表見
[營運任務狀態協議](營運任務狀態協議.md) §二。

### ③ 拉任務內容

```bash
curl -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/order/queryById?id=260828-ST0115"
```

回應是完整的訂單（欄位說明見 §四.2）。要看的是 `payload.stations`——那是班表
排出來的站序與各站計畫時刻。

### ④ 規劃路徑

中心端**不給路徑**，只給「去哪、幾點該到」。車輛是自駕，路徑自己規劃。

站點的座標在你收到的圖資檔裡。三種識別碼都要查得到：

| 形式 | 例 | 在圖資的哪裡 |
|------|-----|------------|
| 停靠點別名 | `station_1` ～ `station_10` | `pointTopology.nodes[].stationId` → 對應設施 id |
| 渡線途經點 | `xo_1_a`、`xo_3_b` | 設施的 `parameters.trackCrossoverPortals[].waypointCode` |
| 場區格位代號 | `E1`、`H1`、`M4` | 設施的 `customName` |

> **座標要取 `refField*M`，不是 `positionMeters`。**圖資裡每個物件都有兩組看起來
> 都像公尺的座標：`positionMeters`／`area.domain` 是**圖面座標**（畫布上的排版位置），
> `parameters.refFieldXM`／`refFieldYM` 才是**現場座標**。兩者不是同一個仿射變換，
> 實測最大差距 685 公尺。取錯的話車會整批出現在圖外，而且沒有任何錯誤訊息。

### ⑤ 回報啟動

```bash
curl -X PUT -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/order/updateOrderProgress/260828-ST0115?status=processing"
```

**這一支是訂單狀態的唯一真相來源。**中心端不採信 MQTT 上的狀態，只認這支 API
的 HTTP 成功回傳。沒呼叫成功，訂單就一直是 `PENDING`，班次紀錄裡這班等於沒跑。

狀態機（不允許的轉移回 `400`）：

```
PENDING ──▶ PROCESSING ──▶ END
                  │
                  └──────▶ FAULTED ──▶ PROCESSING（人工復歸後）
                                   └──▶ END
```

### ⑥ 沿途回報

三個 topic，各自的節奏與 payload 見 §四。**最容易漏掉的是
`operation/update.current_leg.target_station_id`**——那是中心端唯一能把車輛回報
對應回班表站序的欄位，誤點秒數、對外即時 ETA、站端的「即將進站」全部由它推導。
少了它，對外 ETA 的 `next_stop` 對這台車就是 `null`。

### ⑦ 結案與待命

```bash
curl -X PUT -H "x-api-key: <金鑰>" \
  "http://…/order/updateOrderProgress/260828-ST0115?status=end"
```

結案之後**不要停止回報**。真實的車停著也一直在回報位置；停報的話中心端圖台會
沿用最後一次的位置，那台車看起來就卡在終點不動。

待命時要回報**所在的場區格位**：

```json
{
  "vehicle_code": "PMS-01",
  "timestamp": 1787851200000,
  "yard_slot_id": "E1",
  "vehicle_phase": "IDLE",
  "order_status": "IDLE"
}
```

> **報「我人在哪一格」，不是「我的家在哪一格」。**跑完一趟的車停在終點，那多半
> 在正線上而不是場區——這時 `yard_slot_id` 應該留空，只送座標。照著「家」報的話，
> 圖台優先信格位，會把所有車都畫進場區。

## 四、JSON Schema

以下 schema 為 JSON Schema draft-07。時間戳一律是 **13 位 Unix Epoch 毫秒**。
座標一律是**現場座標（公尺）**。

### 4.1 `operation/assign`（中心 ➔ 車端）

Topic `v1/vtms/{vehicle_code}/operation/assign`，QoS 1，retain `false`。

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "OperationAssign",
  "type": "object",
  "required": ["vehicle_code", "timestamp", "order_id", "priority_level"],
  "additionalProperties": false,
  "properties": {
    "vehicle_code": { "type": "string", "pattern": "^PMS-[0-9]{2}$" },
    "timestamp":    { "type": "integer", "description": "Unix Epoch 毫秒" },
    "order_id":     { "type": "string", "pattern": "^[0-9]{6}-.+$" },
    "priority_level": {
      "type": "integer",
      "enum": [100, 90, 50, 40, 30, 20],
      "description": "100 強制召回／90 緊急救援／50 正線營運／40 整備調度／30 出車前測／20 收班回廠"
    }
  }
}
```

```json
    "heading": -3.1415842
  },
  "kinematics": { "velocity": 4.43, "acceleration": 0.05, "angular_velocity": 0.02 },
  "actuation_feedback": { "throttle": 15, "brake": 0, "steering_angle": 0, "gear": "D" },
```

> 位置。回報 8 但實際每秒跑 80 公尺的話，外推出來的位置跟下一筆對不上，畫面會
> 「衝過頭再被拉回」，比不外推還鈍。

### 4.6 `command/execute`（中心 ➔ 車端）與 `command/ack`

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",

  "type": "object",
  "required": ["command_id", "vehicle_code", "timestamp", "status"],
```

## 五、最容易踩到的六件事

| 症狀 | 原因 |
|------|------|
| **車在圖台上完全看不到** | 待命時沒回報位置。沒有 `telemetry` 就沒有那台車，不是「停著所以不顯示」 |
| **車卡在上一趟的終點不動** | 結案後停止回報。圖台的位置快取會沿用最後一次的位置 |
| **所有車擠在場區、角度還各自歪斜** | 待命時報的是「家」的格位而不是**實際所在**格位。圖台優先信 `yard_slot_id` |
| **對外 ETA 的 `next_stop` 全是 null** | `current_leg.target_station_id` 沒填，或填了站體名稱而不是停靠點識別碼 |
| **整備分佈與整備分頁全空** | `line_kind` 把整備標成 `MOVEMENT`。只有 `MAINLINE` 與 `MAINTENANCE` 兩種 |
| **車輛整批出現在圖外** | 座標取了 `positionMeters` 而不是 `refField*M`。兩者不是同一個座標系 |

另外兩個關於畫面順暢度的：

- **車動得一頓一頓**：`telemetry` 頻率跟不上車速。讓每筆之間的位移維持在 10 公尺以內。
- **車衝過頭又被拉回**：`kinematics.velocity` 填了固定值。要填實際位移算出來的值。

## 六、用模擬器對照

本系統附一套參考實作（`syncdrive_t3_simulator`），以**與真車完全相同的路徑**連線：
對外 API 加 MQTT，每台車一組帳密，圖資讀本機檔案，沒有任何內部端點。

它的控制頁有一個「逐車流程」分頁，一台車一個標籤，把上面七個步驟連同**實際送出去
的 JSON** 逐筆列出來：

```
① 連線 MQTT broker
② 訂閱中心端下行 topic
   RECEIVE v1/vtms/PMS-01/operation/assign
③ GET  /order/queryById?id=260828-ST0115
④ 取回任務內容
⑤ 規劃路徑
⑥ PUT  /order/updateOrderProgress/…?status=processing
   PUBLISH v1/vtms/PMS-01/telemetry/update    （每 3 秒取樣一筆）
   PUBLISH v1/vtms/PMS-01/operation/update
   PUBLISH v1/vtms/PMS-01/health/heartbeat
⑧ PUT  /order/updateOrderProgress/…?status=end
⑨ 回到待命
```

週期性回報會取樣顯示，並標示這段期間另外送出幾筆——里程碑不會被沖掉。

接完之後的自我檢查：把你的車接上去，跑一趟，然後打

```bash
curl -H "x-api-key: <金鑰>" \
  "http://34.80.84.224:3100/syncdrive-api/vehicles/eta/by-vehicle"
```

你的車應該出現在清單裡，而且 `next_stop` 帶著 `station_id`、`eta_seconds`、
`arrival_state`。如果 `next_stop` 是 `null`，回頭檢查 `current_leg.target_station_id`。
