# 部署到新伺服器

> 適用於雲端 VM 與進場的實體伺服器——**兩者流程完全相同**，同一個安裝檔、同一支指令。

---

## 一句話版本

在目標主機上：

```bash
tar xzf syncdrive-t3-<版本>.tar.gz && cd syncdrive-t3 && sudo ./deploy/install.sh
```

跑完會印出這台機器的入口網址與帳密。**沒有第二步。**

---

## 一、先確認目標主機符合三件事

| 項目 | 需求 | 不符會怎樣 |
|------|------|-----------|
| **Docker** | Docker Engine ＋ compose plugin | `install.sh` 會停下並告訴你安裝指令 |
| **磁碟** | 至少 20 GB，建議 50 GB 以上 | 會警告；遙測開啟後每天約長 1 GB |
| **記憶體** | 建議 8 GB 以上 | 會警告；資料庫與後端可能不穩 |
| **CPU 架構** | **amd64** | 見下方〈架構必須相同〉 |

安裝包**不含 Docker 本身**——那是唯一需要現場自備的東西。Debian／Ubuntu：

```bash
curl -fsSL https://get.docker.com | sh
```

無外網的環境請向系統管理員索取離線套件。

---

## 二、取得安裝檔

安裝檔由**打包機**產出，不是在目標主機上建置：

```bash
# 在打包機上（目前是 GCP 那台 syncdrive-t3）
./deploy/pack-offline.sh v0.3.0
# → deploy/dist/syncdrive-t3-v0.3.0.tar.gz  約 500 MB
```

把那個 tar.gz 用任何方式（scp、隨身碟）送到目標主機即可。

### 為什麼不在目標主機上建置

在目標主機 `npm ci`、`docker pull`，安裝出來的內容就取決於「**那一天套件庫給了什麼**」。
`node:20-alpine` 這種標籤是可變的，今天拉到的與下個月拉到的不是同一份。於是測試過
的與現場跑的不再是同一份，而這種問題最難查，因為程式碼完全沒動。

建置只發生一次，成品拿去哪裡裝都一樣。所有基底映像都釘在 digest
（`deploy/images.lock`），安裝包裡的 `MANIFEST.txt` 記錄這一包對應哪一個 commit。

### 架構必須相同

打包機的 CPU 架構必須與目標主機相同。開發用的 Mac 是 **arm64**，伺服器多半是
**amd64**——在 Mac 上打的包放到 amd64 機器會以 `exec format error` 收場，而那個
訊息跟真正的原因看起來毫無關聯。`pack-offline.sh` 會先檢查並警告。

最省事的做法是**拿雲端那台 VM 當打包機**：它本來就是 amd64。

## 三、安裝

```bash
tar xzf syncdrive-t3-v0.3.0.tar.gz
cd syncdrive-t3
sudo ./deploy/install.sh
```

`install.sh` 依序做四件事，每一步失敗都會停下來說明原因，不會留下半套狀態：

1. **檢查前置條件** — Docker、磁碟、記憶體、映像包是否齊全
2. **安裝並啟動** — 匯入映像、產生這台機器專屬的帳密與金鑰、設定防火牆、起服務
3. **匯入起始資料** — 班表、時間模板、整備任務、車輛、設施格、地圖
4. **驗收** — 25 項檢查，包含對外邊界是否真的擋住

選項（通常不需要）：

| 參數 | 用途 |
|------|------|
| `--no-seed` | 不匯入起始資料（機器上已有正式資料時） |
| `--yes` | 不互動確認，全部照預設跑（自動化用） |
| `--build` | 在這台機器建置（**只有打包機需要**） |

### 想逐步執行

`install.sh` 只是把三支腳本串起來，沒有自己的邏輯：

```bash
sudo ./deploy/bootstrap.sh     # 安裝
./deploy/seed-restore.sh       # 匯入起始資料
./deploy/healthcheck.sh        # 驗收
```

出問題時可以逐支跑，效果相同。

---

## 四、安裝完成之後

`install.sh` 會印出這台機器的入口與帳密。**每一次全新安裝都會重新產生一套**，
不會沿用其他機器的。

| | |
|---|---|
| 圖台 | `http://<主機>/`　不需帳密 |
| 內部入口 | `http://<主機>/portal`　需內部帳密 |
| 對外入口 | `http://<主機>:3100/`　需對外帳密 |
| MQTT | `<主機>:1883`　帳密見 `deploy/mqtt-credentials.txt` |

### 防火牆

安裝腳本會設定主機層防火牆（ufw 或 firewalld，兩者皆無時會警告）。**雲端還要另外
設定雲端層的規則**：

| 埠 | 對象 | 建議來源 |
|----|------|---------|
| 80 | 我方圖台與文件 | **限制到我方網段** |
| 3100 | 協力廠商 | 廠商網段（靠帳密與 API 金鑰） |
| 1883 | 車端 MQTT | 車輛網段（靠帳密與 ACL） |
| 5432 / 6379 | — | **不要開**，只綁 `127.0.0.1` |

80 埠一定要限制來源：圖台與內部 API 目前沒有登入系統，能連到就能操作。

## 五、更新既有機器

裝新的安裝包即可，同一支指令。資料庫、`deploy/.env` 與所有帳密都會**保留不動**：

```bash
tar xzf syncdrive-t3-<新版本>.tar.gz
cd syncdrive-t3
sudo ./deploy/install.sh --no-seed
```

> **升級前請先備份資料庫。**本專案目前沒有 migration，資料表結構由 TypeORM 的
> `synchronize` 依實體定義調整——欄位改名在它眼中是「刪一欄、加一欄」，可能靜默
> 刪掉資料。

```bash
docker exec syncdrive_postgres pg_dump -U syncdrive_user syncdrive_t3 > backup.sql
```

### 回滾

```bash
./deploy/deploy.sh --rollback
```

會切回上一個通過驗收的映像版本。

---

## 六、資料庫獨立到另一台

改 `deploy/.env` 兩行即可，compose 其餘不動：

```ini
COMPOSE_PROFILES=          # 清空 → 不啟動內建的 postgres
DB_HOST=10.0.0.9           # 指向那一台
```

---

## 七、出問題時先看這三個

```bash
docker ps                          # 哪個容器沒起來
docker logs syncdrive_backend      # 後端的錯誤
./deploy/healthcheck.sh            # 哪一項驗收失敗
```

| 症狀 | 多半是 |
|------|--------|
| 後端反覆重啟、`relation ... does not exist` | `.env` 的 `DB_SYNCHRONIZE` 不是 `true`（全新安裝需要它建表） |
| mosquitto 反覆重啟、`Unable to open pwfile` | 密碼檔擁有者不對，須為 uid 1883 |
| 圖台開得起來但沒有資料 | 起始資料沒匯入，跑 `./deploy/seed-restore.sh` |
| 班表 API 回 404 | 庫內沒有已發布班表——這是正常回應，不是故障 |
| 容器起來了但打不到 | 雲端層防火牆沒開，或來源網段不符 |
