# 載具即時清單資料與協議對照

本文件是「載具管理模組 → 載具即時清單」的實作依據。車端 MQTT payload 維持既有協議；`data_at`、`received_at`、`persisted` 等欄位只存在後端資料庫與瀏覽器 Socket envelope，不加入協力廠商 payload。

## 畫面欄位對照

| 畫面欄位 | 文件章節／既有欄位 | 後端保存 | 前端更新 |
|---|---|---|---|
| 載具名稱 | `vehicles.display_name`；缺值回退 `vehicle_code` | `vehicles` 主檔 | 初始快照；主檔重讀 |
| 行駛速度 | 《車輛動態協議》§四.3 `kinematics.velocity`，單位 m/s | 原始值保存在 `telemetry_payload`；既有 `demo_speed` 只為舊功能相容，不作本頁權威來源 | 快照及 Socket 都由原始 m/s 唯一一次換算為 km/h |
| 電池電量 | 《車輛動態協議》§四.4 `energy.battery_level` | `telemetry_payload.energy.battery_level`；既有 `demo_load` 只為舊功能相容 | 快照／telemetry Socket |
| 駕駛狀態 | 目前四份介接文件沒有駕駛模式欄位 | 不推測、不保存假值 | 顯示「未知」；不以速度推導 |
| 連線狀態 | 《設備健康與異常告警協議》§四.1；以新心跳的後端接收時間判定，預設 5 秒 | `health_fresh_received_at`；相同車端 timestamp 的 Retain／重送不刷新 | 快照依伺服器時間判定；新 health envelope 更新；Socket 連線本身不代表車輛在線 |
| 檔位 | 《車輛動態協議》§四.4 `actuation_feedback.gear` | `telemetry_payload.actuation_feedback.gear`；既有 `gear` 欄只為舊功能相容 | 快照／telemetry Socket |
| 運動狀態 | 《營運任務狀態協議》`vehicle_phase`；速度只供「停止／移動」保守顯示 | `operation_payload`；沒有 operation 時保留速度顯示，不創造車端 phase | operation Socket；無有效資料顯示未知 |
| 目前位置 | 《車輛動態協議》§四.2 `local_pose.position`；《T3 地圖站點與路線清單》本地平面座標 | 原始座標在 `telemetry_payload`；後端解析的 map／名稱／類型／物件 ID 在 `telemetry_derived`，與舊示範欄位隔離 | 快照／telemetry Socket；不把下一站當目前位置 |
| 目前任務 | 《營運任務狀態協議》§五 `order_id`、`task_group`、`vehicle_phase` | `operation_payload`；REST `operation_orders` 另為契約狀態權威 | 顯示全部有效 task，不只取第一筆；MQTT phase 與 REST 訂單狀態分列 |
| 班次 | 《營運任務狀態協議》§三、§五 `trip_code` | `operation_payload` 與 `operation_orders.trip_code` | operation Socket；空值顯示「—」 |
| 最後更新 | 三串流各自 `timestamp` 與後端收到時間 | `telemetry_*_at`、`operation_*_at`、`health_*_at` 分開保存 | 逐串流合併；較晚回來的舊快照不得覆蓋較新的 Socket 資料 |

## 完整資料流

1. 車端依既有 Topic 發送 telemetry／operation／health；QoS、Retain、欄位和值域不變。
2. `MqttController` 驗證 topic 身分並交由既有服務解析；telemetry 的位置仍由 `MapService` 判定。
3. 三串流各自以 `(vehicle_code, data_at)` 防止重複或亂序資料覆蓋新快照，寫入既有 `vehicle_monitor_demo`。歷史 `telemetry_logs` 是否開啟不影響最新快照；示範模擬器更新舊欄位也不會覆蓋本頁的原始 payload／衍生位置。
4. Redis 維持低延遲快取；資料庫快照是重新進頁、後端重啟與 Redis 暫時無資料時的來源。
5. 後端在既有 Socket 事件外，另送內部 `vehicle/state` envelope，明確包含串流、資料時間、接收時間與是否成功持久化；原始 payload 放在 `payload`，不修改成新的車端格式。
6. 前端先建立共用 Socket 訂閱，再請求資料庫快照；依「載具＋串流」比較 data/received time 合併，因此慢快照不會覆蓋新訊息。Socket 重連後重新抓快照對帳。

## 文件與既有程式差異（實作前盤點）

- 舊 `/syncdrive-api/vehicles/snapshot` 只讀 Redis 且固定 PMS01～PMS11，不含註冊但未送資料的載具；本頁改為資料庫註冊集合 LEFT JOIN 快照。
- 舊 DB 快照只有位置、已換算 km/h 的速度與電量，operation／health 僅在 Redis；本次在同表補齊，不另建平行狀態表。
- 既有 Redis anti-drift 會要求 `global_pose`，而持久化定位另要求有效 `local_pose.position`；兩者都是現行《車輛動態協議》的必填資料，任一缺少即拒絕，不自行放寬成第三種格式。
- 舊前端車隊 Hub 只註冊固定車號 listener；本頁使用後端單一車隊 envelope，註冊主檔的新車不需改前端常數。
- `operation/update` 與 `health/heartbeat` 為 Retain；收到事件不等於剛上線。operation 可做最後已知狀態，health 只有 timestamp 前進時才刷新 `health_fresh_received_at`。
- MQTT `vehicle_phase`／`task_group` 是執行狀態；REST `operation_orders.status` 才是訂單契約結案權威。畫面分開顯示，不以 MQTT 自行結案。

- 送入文件格式的 telemetry `3 m/s`，資料庫與畫面均為 `10.8 km/h`；電量 75、檔位 D 與位置同步更新。
- 頁面不重載時，清單與已開啟的 PMS01 單車定位視窗同時收到 `vehicle/state` 更新。
- 刪除 PMS01 的四個 Redis live keys 後，API 仍從資料庫讀回同一筆 10.8 km/h／75% 快照，證實初始畫面不依賴 Redis。
- 相同 timestamp 的 health Retain 重送被拒絕，沒有刷新在線時間；超過門檻後維持離線。
- 測試結束已清除 MQTT Retain、Redis 測試 key 與 PMS01 本次新增的三串流快照欄位。

## 套用與回復

1. 先備份資料庫，再執行 `backend/src/database/migrations/20261013-vehicle-realtime-snapshot.sql`；Migration 使用 `ADD COLUMN IF NOT EXISTS` 與 `CREATE INDEX IF NOT EXISTS`，可重複執行。
2. 依既有方式重啟 backend／frontend，不需新增 port、broker Topic 或外部車端欄位。
3. 若需回復程式，回退本次 commit 即可；資料庫新增欄位留存不影響舊版。確認不再需要快照資料後，才另行人工移除欄位與索引，避免不可逆資料遺失。
