# 訂單排程與執行模型

## 核心邊界

訂單是車輛營運任務的最小執行契約。班表與手動排程是任務來源；未發布計畫不代表已指派訂單。兩者到達發行條件後，均由既有 `OrderService` 建立 `operation_orders`，再以既有 MQTT 指派通知與 REST 內容、狀態回報執行。

```text
已採用班表計畫 ─┐
           ├─ DispatchEngine（同一資料庫 advisory lock）
手動計畫 ─┘       │
                   ▼
              OrderService → operation_orders → MQTT assign
                                      │
                                      └→ 車端 queryById／REST 狀態回報
```

`scheduled_order_entries` 只保存尚未發布的人工輸入計畫與發行結果，不是第二套車端訂單表，也不鏡像 `PROCESSING/END/FAULTED`。發行前不寫入 `operation_orders`，所以車端 `order/active` 與 `queryById` 不會提前看到未到期計畫。

日曆對既有 `operation.daily_plan.<YYYY-MM-DD>` 採用快照只做讀取，不呼叫 `ensureDailyPlan`、不改採用版本也不派單。快照任務發行成訂單後，以 `operating_day + plan_digest + plan_block_id/plan_trip_code` 去重，只保留實體訂單一筆。

## 欄位來源

| 畫面資料 | 計畫階段 | 發行後 |
|---|---|---|
| 顯示名稱 | `scheduled_order_entries.display_name` | 關聯計畫名稱；無計畫時依序回退 `payload.order_name`、`trip_code`、`order_id` |
| 穩定識別 | 排程 UUID | `operation_orders.order_id` |
| 載具 | `vehicle_code` | `operation_orders.vehicle_code` |
| 路線與站序 | 建立當下的 `route_snapshot` | 優先沿用排程快照；其他訂單使用原 `payload.stations` 或 `route_id` |
| 計畫時間 | `planned_start/planned_end` | 同名訂單欄位 |
| 實際時間 | 無 | 中心接收車端 REST 狀態更新的 `payload.actual_started_at`／`completed_at`；舊資料才回退 `payload.vehicle_progress_at`，不得以計畫時間代替 |

路線快照保留任務身分與歷史可讀性；字母 A/B/C 只是介面順序，對外仍使用穩定 `station_id`。

## 日曆投影與時間

日曆分類不是新增車端狀態，優先序固定且互斥：

1. `END` → 結束。
2. 計畫已取消或 `cancel_requested_at` → 取消；執行中仍標示等待車端確認。
3. `FAULTED` 或既有待確認車輛故障 → 異常。
4. `PROCESSING` → 執行中。
5. 未發布計畫或 `PENDING` → 待執行。

日／週查詢以系統設定時區（預設 `Asia/Taipei`）的民用日邊界查詢，`from` 含、`to` 不含；跨午夜任務歸入計畫開始日。民用日只用於管理畫面，不改變既有營運日定義。

後端依日期與分類保留完整計數，但每組只回傳有界筆數（預設 20、上限 200），避免大量班表任務一次塞入瀏覽器。缺少 `planned_start` 的舊訂單另回 `unscheduled_count`，不使用 `created_at` 猜測歸屬日期。

## 發行、冪等與恢復

- 建立計畫以 `request_key` 冪等；同 key 同內容回原結果，不同內容回 409。
- 到期發行與班表使用同一個 dispatch tick、持久開關、提前量／補發窗口與 PostgreSQL advisory lock。
- 實體訂單 ID 由排程 UUID 決定。若建單成功但更新計畫狀態前程序中斷，重跑會先辨識既有訂單，再補記 `PUBLISHED`，不重建訂單。
- 建單／MQTT 路徑失敗會保存錯誤並在補發窗口內重試；逾期後標記 `EXPIRED`，不偽造 `FAULTED` 車端訂單。
- MQTT QoS 只提供既有的至少一次通知語意；車端仍以 REST 對帳，本文不宣稱 exactly-once。

## 內部 API 與權限

| API | 用途 | 權限 |
|---|---|---|
| `GET /syncdrive-api/order/schedule/options` | 可用載具、既有路線與唯讀站序 | `service.scheduled-orders.view` |
| `GET /syncdrive-api/order/schedule/calendar` | 讀取 1–7 日投影；沒有派單副作用 | `service.scheduled-orders.view` |
| `GET /syncdrive-api/order/schedule/detail` | 排程／實體訂單唯讀詳情 | `service.scheduled-orders.view` |
| `POST /syncdrive-api/order/schedule` | 建立未發布計畫 | `operations.dispatch.create` 或 `service.scheduled-orders.create` |

此 API 僅供瀏覽器 Session 與 CSRF 防護使用，不開放車端 API key，也不改動既有 3100 對外路由。

建立排程只能選資料庫中的 `operation_routes`，並保存當下站序／動作摘要與目前已啟用地圖 ID。沒有啟用地圖、路線不足兩站或載具未啟用時，後端拒絕建立，不以第一張圖或前端值補寫。既有資料模型目前沒有 route-to-map 外鍵，因此本輪明確保存建立時的啟用地圖，不宣稱幾何路線 ID 等於營運路線 ID。

`scheduled_order_entries` 是營運排程與稽核資料，不納入一般歷史／遙測自動保留政策；若未來需要清理，必須另訂保留期限與已發布訂單引用保護。

## 本輪刻意未新增

未新增首站手動／自動發車旗標、頂層廣播媒體、任意 payload、站點編輯、循環排程、拖曳改期、人工寫入車端狀態或新的 MQTT topic。行程時間在既有路線沒有可靠資料時顯示「未提供」，不以平均值或零分鐘冒充。
