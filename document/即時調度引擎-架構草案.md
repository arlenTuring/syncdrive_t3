# 即時調度引擎 架構草案

> **狀態：草案，未動工。** 供上完 GCP 之後討論用。
> 本文只做兩件事：把問題定義清楚，以及把需要你拍板的事項列出來。

---

## 一、兩個引擎的分工

| | 排班調度引擎（已有） | 即時調度引擎（要做） |
|---|---|---|
| 產出 | **靜態班表**：哪一列、幾點、跑哪條路線、何時整備 | **當日執行**：誰去做、現在做到哪、慢了怎麼辦 |
| 時間觀 | 一次算完 24 小時 | 持續追蹤，隨事件反應 |
| 對象 | 時間線「列」（匿名） | 真實車輛 `PMS-xx` |
| 失敗形式 | 排不出可行解 | 排得出但現場跟不上 |

排班引擎的輸出**不完整**——它不知道哪一列是哪一台車。這正是即時調度引擎要補上的第一塊。

---

## 二、核心概念：時間線列是「角色」，不是「車」

一列＝一份當日工作清單（跑哪些班次、什麼時候進廠）。它是**計畫的屬性**。
哪一台車來擔任這個角色，是**車隊當下狀態的屬性**——保養到期日、電量、故障、
昨天停在哪一格。

兩者必須分開。如果在排班時就把車綁死：

- 班表只對「某一天、某一種車隊狀態」有效，隔天保養到期的車換了一批就要重排
- 一台車故障就得重跑整個排班引擎，而排班引擎跑一次是十幾道幾何處理
- 泛用性平台的前提消失——班表變成綁定特定車隊的一次性產物

所以：**排班引擎產出角色，即時調度引擎每日把角色綁到車。**

你提到的那件事正好是這個結構的證據：時間模板裡倒數第二、第三列排的是保養，
意思不是「第 10 台和第 11 台車要保養」，而是「**每天有兩台該保養的車去擔任這兩個
角色**」，牠們原本的班次由別台接手。角色固定，人選每天不同。

---

## 三、每日綁定：這是一個指派問題

每天固定時刻（例如 04:00），對「N 個角色 × M 台車」求一組指派。

**硬約束（違反就是不可行）**

| 約束 | 資料來源 | 現況 |
|---|---|---|
| 該保養的車必須被指派到含保養區段的角色 | 車輛保養到期日 | **缺**——`vehicles` 資料表目前只有代號、名稱、啟用旗標 |
| 故障／停用的車不可指派 | 健康協議 `overall_health` | 有（Redis + 事件） |
| 角色首班起點站，車必須到得了 | 車輛停放位置 ＋ 路網拓樸 | 有 |

**軟成本（可行解之間排序用）**

| 成本 | 理由 |
|---|---|
| 空跑距離 | 車停在 P3、角色首班從 N2W 出發，中間那段是純成本 |
| 電量與充電區段的匹配 | 低電量車配到含充電區段的角色 |
| 輪替公平性 | 同一台車不該天天跑最重的角色 |

規模很小（11 台 × 11 角色），匈牙利演算法或直接列舉都跑得完，**不需要近似解**。

**要你決定的**：
1. 每日綁定的時刻定在幾點？必須早於當天第一班發車，且晚於前一天最後一班收班。
2. 保養週期怎麼記——固定天數（每 N 天）、里程、還是人工排定？這決定「到期日」欄位長什麼樣。
3. 綁定要不要人可以覆寫？(建議要，並留稽核紀錄——現場一定會有引擎不知道的理由)

## 四、每日交班：一個明確的切點

```
    ─────────────── 前一營運日 ───────────────┤ 交班時刻 ├─────────────── 當日 ───────────────
                                              │
    班表：已發布、已部署（角色層級）           │  綁定完成 → 班表才「完整」
    車輛：昨日狀態                            │  訂單：當日全量產生
                                              │  模擬器／車端：這一刻取得當日工作
```

交班時刻之前，部署的班表**沒有車輛對應**；之後，綁定當日凍結。

**為什麼要凍結**：中途若重新求解整組指派，一台車故障會導致全隊重新洗牌——
所有車的當日工作都變了，現場無法執行。中途的異常必須以**增量**處理：
只動受影響的那幾趟，其餘不動。

**要你決定的**：中途故障時的處置優先序。可選：
- **接管**：把剩餘班次交給待命車（需要有待命車）
- **併班**：後車吸收前車的乘客，班距拉大但不斷班
- **跳班**：該趟取消，回報 PPHPD 缺口

## 五、訂單下發：模擬器只解訂單，不讀班表

你說的這條規則我認為是對的，而且應該寫死成架構限制：

> 模擬器（以及日後的真車）拿到的是**訂單**，不是班表。它只需要知道
> 「我現在要去哪、做什麼」，其餘一概不管。

這條線劃清楚之後：

- 車端不需要理解班表格式、不需要跟著改版
- 誰在執行、執行到哪，只有一個真相來源（即時調度引擎）
- 換成真車時，車端的介面完全不變

現有的[營運任務狀態協議](營運任務狀態協議.md)已經定義了訂單生命週期
（REST 建立契約、MQTT 回報進度），**這一層不必重做**，即時調度引擎接上去即可。

**要你決定的**：下發時機。
- **全量**：交班時把當日訂單一次給完。車端可預先規劃，但延遲發生時要大量改單。
- **即時**：只給下一趟，跑完再給下一趟。對延遲最靈活，但車端看不到未來。
- **混合（建議）**：下發「下一趟」為契約，另外預告後續 2–3 趟供參考、不具契約效力。

## 六、延遲追蹤：資料已經有了，缺的是「決定」

即時 ETA 介面已經在做計畫值與即時值的比對，每一筆都帶 `delay_seconds`。
但那是**回報**——它只描述現況，不做任何決定。

即時調度引擎要多做三件事：

1. **誤點傳播**：這一趟晚了 90 秒，下一趟還來得及嗎？同一台車的後續班次會不會
   連鎖遲到？這是沿著「該車當日工作清單」往後推算的問題。
2. **門檻與處置**：晚多久要介入？介入方式是什麼（見第四節）。
3. **回寫**：處置決定之後，訂單要改、對外的 ETA 要跟著更新——否則廠商看到的
   還是原班表，現場卻已經換了做法。

## 七、對外交付：MQTT 還是 API

兩者不是二選一，看的是「資料的性質」：

| 性質 | 適合 | 對外項目 |
|---|---|---|
| **狀態**（可重複讀、讀到最新即可） | HTTP 輪詢 | 當日班表、各站 ETA、車輛位置 |
| **事件**（發生一次、錯過就沒有） | MQTT 推播 | 班表換版、班次取消、車輛故障 |

現有的兩支即時 ETA 是輪詢式的，符合第一類；規格書第八章也已經寫好輪詢規範。
**建議維持輪詢為主**，MQTT 只用在真正的事件——推播要處理離線重送、順序、
去重，成本比輪詢高得多，只有「錯過就沒有」的資料值得付這個成本。

**要你決定的**：廠商要不要收「班表換版」事件？如果他們接受每日固定時刻重抓一次，
就完全不需要 MQTT，對外面只留 HTTP 一種介面。

## 八、資料模型缺口

要動工之前必須先補的：

| 缺口 | 說明 |
|---|---|
| 車輛保養到期 | `vehicles` 表沒有任何保養相關欄位，指派的硬約束無從判斷 |
| 每日綁定表 | 角色 → 車輛，含綁定時刻、依據、是否人工覆寫 |
| 班次執行紀錄 | 計畫 vs 實際、誤點、處置。驗收項目 2-201 要求「班次運行紀錄可查」 |
| 部署版本 | 目前 `usage_status` 只有 idle／in_use 兩態，沒有「哪一天用哪一版」 |

---

## 九、討論時要先拍板的六件事

1. 每日綁定時刻
2. 保養週期的記法（決定資料表欄位）
3. 綁定可否人工覆寫
4. 中途異常的處置優先序：接管／併班／跳班
5. 訂單下發時機：全量／即時／混合
6. 對外要不要 MQTT 事件，或只留 HTTP 輪詢
