## 四 事件管理前端

側欄保留「事件管理清單」一個事件入口，刪除原獨立「歷史事件檢視」入口；「影像資源管理」「即時影像監控」保持原有獨立功能。事件頁容器建議 EventManagementPage，內部 tab key 使用 pending／confirmed／history。前端可重用／改造 LiveEventsPage、HistoryEventsPage 與共用表格，不讓兩個舊頁入口繼續並存。

### 頂部改為三個標籤

- 截圖整段區域全部刪除：內頁「即時事件管理」標題、綠點即時連線文字、待確認／嚴重／警告 badge、近 24 小時已確認、最後更新與時區文字，以及下方範圍／安全說明。不能只隱藏文字留下原區塊高度。
- 原位置換成本站一致的標籤列，依序「待確認」「已確認」「歷史事件查詢」，下方直接是作用中內容。殼層頁首／麵包屑改名「事件管理清單」，不在內頁又堆一排重複標題。
- 預設待確認，可在待確認／已確認標籤文字旁用小數字顯示後端真實總數，但不再另建頂部統計 badge／說明區。歷史標籤未查詢前不顯示假筆數或全庫數量。
- 連線中斷／送出失敗等必要提示放作用中內容的短錯誤列，平時不占截圖原區域。不把移除的工程說明換個位置重新常駐。
- tab 有 aria-selected、鍵盤切換與明確作用中樣式。換 tab 不同時掛載所有資料清單的輪詢與播放器，也不讓隱藏 history 自動查詢。

### 待確認標籤

- 自動載入所有仍保留且 is_acknowledged=false 的事件，不受近 24 小時／當日限制；無日期、載具或狀態篩選工具列。新持久化事件 ≤3 秒更新，不能必須按搜尋或手動刷新才顯示。
- 表格：發生時間（日期至秒）、載具／來源、類型、嚴重度、事件摘要、確認緣由／處置操作、詳情。**不顯示處理狀態／目前狀態欄，也不逐列再畫「待確認」badge。**
- 依嚴重度 CRITICAL／WARNING／INFO，之後發生時間降冪、內部 ID 降冪穩定排序；首批 8 筆，有界 cursor／載入更多，資料量大時虛擬化。未載入的待確認仍計入真實標籤總數。
- 每筆用列內輸入或列內展開區填「確認緣由」，標示必填，placeholder 例如「請填寫已確認的狀況或處理緣由」。trim 後 1–500 字，不能只空白／換行或帶預設假緣由；後端以同樣規則驗證。
- 使用者填妥並按「確認事件」才送出，缺緣由在該列精準提示。停用是因資料無效／送出中，不以無操作權限將按鈕藏掉；無權點擊沿用 auth.require 提示。
- 只鎖該筆送出，其他事件仍可到達與操作。請求綁中心端 id，不用 row index。新事件插入時保留輸入草稿、焦點及捲動錨點，不把緣由套到另一筆。
- 成功收到後端結果後，該筆從待確認移除、進入已確認的資料集合，兩個標籤計數同步。**不自動把使用者跳到已確認標籤**；顯示短成功提示即可。若已確認頁尚未載入，標記失效，切入時載入最新資料。
- 失敗時保留原列與緣由，允許重試；不能先把列搬走。兩人競爭確認時，後到者取得既有結果並同步移出，不覆蓋先成功者的緣由／身份／時間，也不重複記成功稽核。

### 已確認標籤

- 切入後自動查詢 is_acknowledged=true 的仍保留紀錄，依確認時間降冪、ID 降冪，分頁／cursor 有界；**不沿用舊近 24 小時限制**，標籤數字與集合一致。
- 表格：發生時間、載具／來源、類型、嚴重度、摘要、確認緣由摘要、確認人、確認時間、詳情。長緣由可截斷，完整內容在詳情中看。
- **不顯示處理狀態／目前狀態欄，不逐列重複「已確認」badge，不提供再次確認或修改緣由的輸入。** 不憑本次需求新增撤回／取消確認／重新開案。
- 既有 acknowledged=true 但確認時間或緣由缺漏的舊資料仍在此標籤可查，顯示「舊資料未記錄」，不使用目前時間、目前操作者或假緣由回填。NULL 確認時間排序明確放最後，保留可追溯排序。
- 同一事件在待確認與已確認標籤不能長期同時存在；使用者切頁、重連、其他人操作後重新對齊後端狀態。

### 歷史事件查詢標籤 先空白 再查詢

- 第一次進入整個頁面或首次切到 history，表單可有最近 7 天的日期預填，但結果為空、尚未查詢，顯示「請設定條件後按查詢」。不得自動載入事件資料／查詢總數／預設最近紀錄。
- 允許初始化 options／網站時區，不允許因 options 載入、component mount、切換 tab、日期預填、來源 invalidation、背景 Socket、自動重試等觸發 fetchEvents。
- 狀態明確區分 idle（未查詢）、loading、success（含查無資料）、error；不能拿 items=[] 同時當尚未查詢與沒有結果，未查詢也不顯示「載入中」或「共 0 筆查詢結果」。
- 保留日期、載具、事件類型及必要嚴重度／來源條件，按「查詢」或明確 Enter 才產生 appliedQuery 並執行；日期／條件無效不發請求。結果每頁 8 筆，穩定 snapshot、排序與 1,000 筆 CSV 上限沿用。
- 只有 hasSearched=true 且有 appliedQuery，才允許分頁、排序、重試、匯出；未查詢時不呼叫 export。匯出／分頁使用已套用條件，不使用尚未按查詢的表單草稿。
- 「重置」清表單／回預設、結果、總數、snapshot、頁碼及錯誤，回 idle，**不自動查詢**。在同次進頁切 tab 可保留使用者已查詢結果；離開事件頁重新進入預設待確認，history 重新 idle。
- 歷史列表只查不處置，不放處理狀態欄／狀態篩選／確認按鈕。查詢範圍可同時包含待確認和已確認，詳細確認紀錄在唯讀詳情與 CSV 可看；不能因隱藏欄位就刪後端證據。
- 舊歷史 deep link 可導到本頁 history 並預填時間／來源，但仍要使用者按查詢才載入結果，不繞過空白預設。eventId 直達詳情可依明確點擊查單筆，不等於自動查歷史清單。

### 三標籤共用且完整的唯讀詳情

本次「詳情一併配上」落實為三個標籤都有詳情入口，點擊按中心端 id 讀單筆並呈現相同完整資料；不臆測另加未指定的攝影機預覽或自動執行處置。

- 頂部呈現該事件待確認／已確認的唯讀摘要；已確認顯示確認緣由全文、確認人、確認時間，待確認顯示尚未確認。列表刪狀態欄不代表詳情也要抹除狀態。
- 其後有原始 event_id／中心 id、完整發生與接收時間及來源時間有效性、來源／載具、類型、嚴重度、事件內容、位置、脫敏原始資料及操作軌跡。
- 既有 acknowledgement_note 作確認緣由的唯一儲存欄位；欄位標籤統一「確認緣由」，不能 UI 說備註選填、另一處說必填。legacy 無資料如實標示。
- 詳情沒有確認表單、再次確認、緣由修改或「看過就自動確認」。待確認時需要操作，可提示回「待確認」標籤原列，不能在詳情偷偷開第二套流程。
- 詳情開啟期間若另一人完成確認，可由授權 invalidation 重取**該單筆**，更新摘要與操作軌跡；這不觸發 history 清單的第一次查詢。
- 有權限的事件回放保留前後各 30 秒、固定載具與高亮、軌跡／影像時間對齊；影像歷史依原規則到影像資源管理的子畫面。非載具事件不偽造車輛，缺段與時間不可用如實顯示。
- 確認只代表中心端已確認，不下發車控、不自動清故障／解除降級、不代表設備恢復。這是後端業務邊界，無需把截圖的長說明再放回首頁。

### 共用容器與即時更新

- 三標籤共享選中事件 id、授權與有界事件通知協調，tab 內保留各自游標／捲動／查詢狀態。只能有一份必要 Socket 訂閱，切 tab 不倍增 listener；卸載時清理。
- 待確認與已確認後端集合分開分頁，不能 GET /events/live 取前 8 筆混合資料後在前端 filter 假裝兩個 tab。處理後以同一真實更新／失效結果協調兩個集合。
- 重連重新取得當前集合與總數，不持續使用截斷新增資料的舊 snapshot；history 已查詢結果保留 snapshot、不因背景新事件跳動，未查詢時仍 idle。
- 待確認／已確認內的資料更新仍 ≤3 秒；滾動／填緣由時維持錨點與 rowId。讀取失敗時可以短提示與 retry，但不得因此搬回截圖那排永久資訊。

### 影像資源管理與即時影像監控

影像前後端、來源儲存設定、版面與歷史入口統一依唯一影像指示執行；本節不重複提供可能衝突的規格。事件回放繼續共用該服務，歷史深連結進「影像資源管理」的歷史子畫面，格子／監控標籤頁不再決定錄影需求。

## 五 日誌管理前端

側欄建立「日誌管理模組」，提供四個獨立子頁，共用表格／詳情／匯出基礎元件。這不是載具管理的「運行管理紀錄」，不要合併頁面或拿車輛遙測當使用者稽核。

所有日誌基本欄位：日誌編號、完整時間、來源 IP、日誌類型、內容、查看詳情；補充顯示操作者與結果，避免只靠長句辨識。預設最近 7 天、每頁 20 筆屬實作設計，可按現站分頁慣例調整。

| 子頁 | 篩選 | 詳情內容 |
| --- | --- | --- |
| 系統操作紀錄 | 時間、使用者、類型；可補關鍵字／結果 | 操作者、目標、動作、時間、IP、結果、失敗原因、脫敏異動摘要與追蹤 ID |
| 權限異動查詢 | 時間、相關使用者、角色；可補異動類型 | 操作者與被異動對象分開呈現；帳號／角色／權限關聯、授予／撤銷、異動前後差異 |
| 營運操作紀錄 | 時間、操作類型、載具；可補操作者／結果 | 班表部署／調整、派遣、路線、降級、門控、速度等真實重要操作及業務紀錄關聯 |
| 登入登出紀錄 | 時間、帳號；可補登入成功／失敗／登出、IP | 帳號、結果、IP、裝置資訊、失敗原因；保留現有 LOGIN_FAILED，不因正式範例僅寫登入登出而隱藏 |

- 權限差異用可讀名稱呈現新增／移除項目，另保留 ID；新增沒有 before、刪除沒有 after 須正確處理。
- 帳號、角色、載具改名或刪除後，舊日誌仍可理解；以操作當時名稱快照為準，缺少快照時清楚標示目前名稱／未知。不得追溯捏造歷史名稱。
- 日誌為唯讀，不提供更改、刪除或補寫既有日誌的前端 API。資料清理仍集中在已授權的資料管理機制。
- GET 日誌清單與輪詢不產生新的操作日誌，避免查日誌導致無限成長。匯出可記錄一次稽核，不能逐列再寫一次。

## 六 後端與 API

沿用 NestJS、TypeORM、既有 REST 前綴、session、CSRF、Guard、DTO 驗證與錯誤格式。以下為建議路由，先檢查衝突，再依現有命名整理：

| 方法與路徑（均在 `/syncdrive-api` 下） | 用途 |
| --- | --- |
| GET `/events` | 有界分頁事件查詢，供即時及歷史頁共用 |
| GET `/events/export` | 目前查詢條件 CSV，最多 1,000 筆 |
| GET `/events/live?bucket=pending`／`bucket=confirmed` | 分開的待確認／已確認集合與總數、游標；不再混合或限制近 24 小時 |
| GET `/events/:id` | 事件詳情，使用中心端內部 ID |
| POST `/events/:id/acknowledgement` | 必填確認緣由；原子確認、寫入稽核並協調兩標籤 |
| GET `/events/:id/playback` | 有權限的軌跡／影像時間窗與來源資訊 |
| GET `/logs/system`、`/logs/permissions`、`/logs/operations`、`/logs/authentication` | 四類日誌查詢 |
| GET 上述各類 `/export` | 沿用相同篩選器的 CSV |
| GET 上述各類 `/:id` | 各類有權限且已脫敏的詳情 |
| GET `/video/sources`、`/video/streams/:id`、`/video/recordings` | 實際來源、受保護播放資訊與歷史片段查詢；依 provider 契約調整 |

實作要求：

1. 靜態 `export` 路由不能被 `:id` 吃掉。任何詳情都要檢查該資料類別的權限，不只檢查已登入。
2. DTO 限定日期、enum、ID、字串長度、頁碼／pageSize 上限與排序白名單。使用參數化 QueryBuilder，不接受前端 SQL、任意資料表名、任意 ORDER BY。
3. 清單回傳 items、total、page、pageSize；事件可帶查詢上界／快照資訊。同時間以主鍵打破排序平手，避免重複／漏列；bigint ID 以字串傳輸，不轉成可能失真的 JS number。
4. 列表只讀必要欄位，大 JSON／差異／原始內容由詳情按需讀，禁止每列 N+1 讀取帳號或載具。
5. 過去帳號／車輛已刪除仍可查歷史。下拉查詢選項要能輸入歷史識別碼或由歷史資料索引取得，不能只列目前在線車。
6. Socket 僅在資料持久化成功後通知；重連需 REST 補查，寫入失敗不能先讓前端顯示成已保存。延續現有 MQTT topic 與 payload 契約，不新增必填車端欄位。
7. 事件來源標準化：VEHICLE／FACILITY／SYSTEM，保留 sourceId、原始 event_id、發生與接收時間、類型、嚴重度、內容、原始有效資料。SCADA 與系統事件走實際 adapter，不憑空新增外部協議。
8. 保留現有 `securityEventDedupKey()` 語意：同車同 event_id 同 timestamp 的 QoS1 重送不新增；不同車撞 ID 或同車不同 timestamp 不能互相覆蓋。資料庫唯一約束處理併發，不只先查再 insert。
9. 不同來源使用有命名空間的去重鍵，避免設施事件撞上車輛事件。時間不合法／缺漏依既有接收契約處理並標示來源時間不可用，不能悄悄把接收時間冒充真實發生時間。
10. 人工確認從待確認標籤的事件列觸發，採單次交易或條件更新，寫確認欄位與操作稽核，成功後推送 invalidation。不可讓一般 PATCH 修改原始事件內容。
11. 影像位址只由允許的來源配置解析，不能提供任意 URL 代理造成 SSRF。密碼、NVR 管理憑證、長效權杖不得送到 UI、CSV、Socket 或日誌；短效播放授權須有到期與存取限制。

## 七 資料庫與稽核寫入

### 事件

優先擴充既有 `security_event_logs`，不要建立與儀表板、歷史回放分離的第二套事件真相來源。對照現有 schema 補 source_type／source_id／source_name_snapshot 等必要欄位，以及 acknowledged_by／acknowledged_at／acknowledgement_note。若設施／系統事件沒有 vehicle_code，調整為可空並修正所有受影響查詢；不能拿虛構車號繞過 NOT NULL。

保留原始 event_id、既有內部主鍵及 dedup_key。審查 enum 是否足以描述正式來源；需要擴充時用 migration，不能為了顯示未對接類型自行產生告警。內部 SYSTEM_HEALTH_DEGRADED 等與車端事件契約仍須區分。

事件若需要多次處理軌跡，才加小型處理歷程表；本次單次確認可直接用確認欄位加既有稽核表完成，不預先搭建工單系統。

### 四類日誌

- 延用 `operator_action_logs`，補明確的 SYSTEM／OPERATIONS 分類、target_type／target_id、操作者與目標名稱快照、request/correlation ID；沿用已存在欄位，不新增同義欄位。舊資料只在可可靠判定時分類，不可硬套目前名稱。
- 延用 `permission_change_logs` 的 before_value／after_value、targetType、changeType，補足可查詢的相關帳號／角色及名稱快照。注意操作者和異動對象是不同人。優先用型別化欄位／有限索引，避免每次掃所有 JSON。
- 延用 `login_logs` 的 LOGIN／LOGOUT／LOGIN_FAILED、帳號、來源 IP、user_agent、原因。只記錄真實 logout；session 到期不是使用者按登出，如需表達應有獨立類型。
- 不把 system debug、console、`dev-log` 排班引擎輸出直接當成正式系統操作稽核。錯誤追蹤與行為稽核是不同資料。
- 操作者取後端驗證 session；自動任務記 service/system 身分；外部主體保留來源。禁止相信 body.operatorId。IP 由正確設定的受信任反向代理鏈取得，不能全信任任意 X-Forwarded-For。
- 盤點既有 AuditService 所有呼叫點，補齊系統設定、地圖／設施、載具、媒體、班表／部署、派遣、路線、降級、門控、帳號角色等實際修改。已有專用權限／登入日誌的動作避免重複計數，分類規則要有明確對照表。
- 記錄 SUCCESS／FAILED／REJECTED 的真實意義。API 接受命令、MQTT 發送、車端 ACK、任務完成不等價；稽核保存操作結果並用 correlation ID 連結 command／order／degraded 紀錄，不把中心端送出直接寫成車輛執行成功。
- 不整包存 request headers/body。白名單保存前後差異，剔除密碼／hash、cookie、session、CSRF、API key、影像憑證；錯誤與匯出也必須脫敏。
- 現有 AuditService 會 catch 寫入錯誤並只打 logger；不能把此行為當成符合「1 秒內寫入」。一般可交易的管理異動與稽核同交易提交，失敗回滾；可擴充 AuditService 接受 EntityManager，避免各模組自己複製寫入。
- 即時安全控制不可因日誌故障而失去緊急控制能力；如無法同交易，須明確回報稽核降級並有有界、可監測、可重試的持久化機制，避免無限記憶體佇列或悄悄漏記。區分已下發控制與尚未下發，不可為了稽核重試再發同一車控。

### 索引與 migration

依實際篩選加入時間＋ID、載具＋時間、來源＋時間、操作者＋時間、分類＋時間、目標＋時間等必要索引；避免每個欄位都建索引。用 EXPLAIN 與代表性資料驗證最常用路徑。

正式環境禁止靠 TypeORM synchronize 改表。新增可重跑／符合專案 ledger 的 migration，先確認先後依賴：表存在後才能新增索引或 retention 設定；enum 變更依 PostgreSQL 交易限制安排。測試空 DB 與現有 DB 升級，保留舊資料、原始 ID 及既有 SQL 儀表板相容性。不能為部署通過刪除 migration ledger、清空 DB 或重建全部資料表。

## 八 權限與即時授權

現有 `access.constants.ts` 的事件權限為 `events.events.view/manage/export`，目前程式已啟用，並已有 `events.video.view`。請沿用或明確遷移，不創造兩組互不相通的代碼；影像設定與歷史權限依影像專項文件擴充。

- 事件 view：清單、詳情；manage：人工確認；export：匯出。回放再檢查軌跡與影像的對應權限，不能因有事件 view 就洩漏影片或完整軌跡。
- 為影像檢視／回放，以及四類日誌各自的 view／export 補齊 registry、角色編輯選項、前後端對照與測試。沿用現有 module.resource.action 格式；具體名稱在實作對照表中記錄。
- 不默認給所有帳號開放權限；依現有管理員授權政策做 seed／migration，現有角色不意外擴權。
- Socket 不可用「具有任意 `.view`」當成可接收日誌內容的資格。若使用通用 invalidation 只發無敏感資料的失效訊號，實際資料仍由授權 REST 查詢；有內容推播必須有專屬權限房間。
- session 到期、帳號停權或權限撤銷後，既有 Socket 和播放授權也須失效；不能只在初次連線驗證。
- 若使用既有 SQL datasource，檢查它是否繞過日誌／影像的新權限。不允許只封 REST，但讓無權使用者透過任意 SQL 讀取同一資料；至少測試此旁路並在交付中說明結果。

## 九 匯出 保存與容量

1. 清單與匯出共用篩選／排序建構器，不能清單查 A、CSV 出 B。事件 CSV 限 1,000 筆，與當頁 8 筆無關；超過時顯示總數、將匯出前 1,000 筆及排序規則，不能默默截斷。
2. 日誌正式規格未訂筆數上限；本次建議同樣最多 1,000 筆並明示，避免大量稽核一次塞入記憶體。若已有共用匯出規則，沿用並說明。
3. 使用 UTF-8 BOM、正確 CSV 引號／換行轉義。人類可讀欄位防試算表公式注入，同時保留機器原值的可還原方式與欄位說明，不能悄悄更動事件原始語意；不直接匯出未脫敏整包 params。
4. 檔案含完整時間與時區、原始 ID／代碼、來源、車輛、類型、狀態等適用欄位，與畫面同義。正確設定 Content-Disposition，不用使用者輸入拼任意伺服器路徑。
5. 匯出採有界查詢與串流／合理緩衝；每次匯出使用固定查詢上界，避免過程中新增資料造成重複。保留下載失敗／取消處理。
6. 對接既有資料管理的手動／自動保存政策；不新增另一套 cron。事件、操作、權限與登入稽核需分開設定，不因模擬遙測的短保存週期一併刪除正式稽核。
7. 不預設啟動破壞性刪除；若資料管理尚未支援某表，先加入範圍與影響預覽，依既有確認流程啟用。保存政策與官方稽核需求有衝突時明列。
8. 不把每次頁面刷新、telemetry、Socket 心跳都寫成操作紀錄；不以大量模擬運行充當驗收。用有界 fixtures、隔離測試 DB，完成後清理本次測試資料。

## 十 驗收與交付

請分批完成，每批跑相關檢查，不要只截圖或只測 HTTP 200：

1. 前端：兩模組導覽與權限、四類日誌、事件管理清單三標籤、歷史初始空白／明確查詢、8 筆有界載入、待確認必填緣由與跨標籤移動、排序同時刻穩定性、空資料、錯誤、完整日期、跨日、共享深色下拉／日期控制、彈窗不裁切。用真實瀏覽器核對桌面與較窄視窗。
2. 事件：兩車同 ID、同車重送、不同 timestamp、併發重送不覆蓋／重複；接收失敗不推成成功；確認冪等、兩人併發、無權限、CSRF，以及確認不觸發任何車控。
3. 即時：初始載入、斷線重連取得新上界補查、自動到達、捲動錨點不跳動、listener 清理、登出／撤權後停止資料存取。
4. 回放：事件前 30 秒、跨日、固定載具、高亮、上下幀、seek／倍速／暫停同步；單側無資料與影像缺段；不使用即時位置填補歷史。
5. 日誌：真實修改產生一次正確稽核；一般設定、班表部署、派遣、降級、門控及權限授予／撤銷、登入成功／失敗／登出；交易回滾、不信任假 operatorId／偽造 IP、歷史改名／刪除、查日誌不再產生日誌。
6. 資安：四類權限隔離、直接 URL／API／Socket／SQL datasource 旁路、secret 脫敏、CSV 公式注入、無權限匯出／影片拒絕、任意串流 URL 代理拒絕。
7. CSV：0、1、8、1,000、超過 1,000 筆；中文、引號、換行、篩選一致、排序與截斷提示、日期秒與時區、取消與失敗。
8. 資料庫：新建與原有資料升級、migration ledger、舊儀表板事件 SQL、保留原始 ID、索引查詢計畫、保存政策不誤刪其他資料。
9. 效能依第一節正式時效逐項量測，記錄資料量、並發、環境與測量起訖。影像增加 12 路的本次需求，與官方 11 路基準一起驗證；測試串流可驗證管線，真實來源與 ≥10 Hz 效能另在目標環境量測，結果列於工程驗收紀錄。

交付以下內容：

- 可運作的前後端、migration、必要配置範例與更新後 Swagger／API 型別。
- 官方條款 → 畫面 → API → 資料表 → 測試的精簡對照表。
- 操作與權限代碼清單、稽核覆蓋範圍、資料分類／保存說明。
- migration 執行順序與 GCP 部署步驟，含實際影像 provider／閘道需求；不自行部署或對正式 DB 做破壞性操作。
- 執行過的測試與效能結果；文件中英文 8／3 筆矛盾、外部 SCADA／影像契約缺少、未驗證環境等必須如實列出。

依下表推進，不要完成畫面後就交付；每階段結束留下可核對的測試結果，繼續下一階段。

## 十二 前後端資料契約補充

沿用現站 DTO 命名方式，以下定義資料語意與必要項目，不要求把 camelCase 與 snake_case 混用。

- 事件查詢：`from`、`to`、`vehicleCode`、`eventCode`、`severity`、`sourceType`、`acknowledged`、`page`、`pageSize`、`sortBy`、`direction`。from/to 用帶時區的 ISO 8601 或專案一致的 epoch 毫秒；不可同一參數混用秒與毫秒。
- 事件回應：中心端 `id`、來源 `eventId`、`sourceType/sourceId/sourceName`、可空 `vehicleCode`、`eventCode`、`severity`、發生時間及其有效性、`receivedAt`、摘要、確認狀態。已確認列表需有確認緣由摘要、確認人及時間；詳情另含脫敏 location／params／detail 與緣由全文。
- 確認 request 沿用 note 作必填確認緣由（trim 後 1–500 字），以及必要的併發版本資訊，不接受 actor／確認時間／已解除故障等客戶端宣告；response 回傳後端最終確認結果與是否已被其他人確認。
- 日誌查詢：共用時間、操作者、動作類型、結果、關鍵字、分頁與排序；各類再提供角色、被異動帳號、載具等適用條件。任何條件不適用該類時應驗證拒絕，不能默默忽略造成查錯資料。
- 日誌回應：`id`、`occurredAt`、`sourceIp`、日誌分類／類型、操作者識別與當時名稱、目標識別與當時名稱、可讀內容、結果；詳情再載入允許的前後差異、失敗原因與 correlation ID。
- 回放 response：事件時刻、請求時間窗、軌跡實際可用範圍、影片實際可用範圍、缺段、來源及受保護的播放資訊；UTC 時刻與媒體偏移分開表示。
- 錯誤：400 為非法條件；401 未登入；403 權限不足；404 找不到／已依保存政策移除；409 用於確實存在且無法自動合併的版本衝突；外部影像不可用回明確的來源狀態與適當錯誤，不回成功空影片。若既有狀態碼契約不同，沿用並記錄。
- 整理最終 DTO／Swagger，前端 API 層集中處理型別、下載與錯誤，不在每個頁面散寫不同格式。

## 十三 可執行的測試與建置要求

以下命令依目前 package.json 與測試 runner 核對。執行前確認 lockfile、專案 Node 版本及現有依賴；優先使用現有依賴，缺少時才依專案規則安裝。不要為文件測試另建一套 runner，也不要擅自更新整包依賴。
