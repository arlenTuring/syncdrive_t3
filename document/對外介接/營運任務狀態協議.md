# 營運任務狀態協議 (Operational Protocol) 規格書

> 目前版：2026-09-18。站點以 [T3 地圖清單](T3地圖站點與路線清單.md) 為準；訂單新規格見 [錯誤與對帳](訂單API錯誤與對帳.md)。

## 一、 協議概述

本協議為 SyncDrive-T3 系統的營運核心，負責同步車輛的業務邏輯狀態與任務執行進度。本系統採用 **「REST API 交易」** 與 **「MQTT 狀態流」** 的混合架構，並嚴格定義兩者的權責邊界：

* **REST API（資料庫交易權威/契約）**：處理具備「契約性質」的絕對狀態變更（如訂單成立、任務內容拉取、任務結案）。車輛監控系統端資料庫的狀態判定，應以 REST API 的 HTTP Status 成功回傳為準。
* **REST 認證**：車端呼叫下列 API 須帶 `X-API-Key` 標頭（與對外 API 同一把金鑰）。
  對外開放的三支為 `GET /order/queryById`、`PUT /order/updateOrderProgress/{id}`、
  `PUT /order/action/{actionId}`；`POST /order/save` 是車輛監控系統端建立訂單用，不對外開放。
* **MQTT 連線認證**：車端一律連 **8883**，TLS 雙向驗證；客戶端憑證的 CN 須等於
  自身 `vehicle_code`。詳見
  [MQTT 通訊架構與 Topic 命名規範](MQTT%20通訊架構與%20Topic%20命名規範.md) §三。
* **MQTT 協議（狀態高頻通知）**：處理「高頻營運數據」的雙向推播。包含車輛監控系統端下發的發車觸發，以及車端持續回報的微觀任務進度。車輛監控系統端不得單憑 MQTT 訊息單獨修改資料庫的訂單契約狀態。
* **單一真值源 (SSOT) 聲明**：車端 (Vehicle) 為 `vehicle_phase` 與 `overall_health` 的**唯一狀態寫入源 (Single Source of Truth)**。車輛監控系統端僅負責狀態的聚合與展示，嚴禁車輛監控系統端主動覆寫，以徹底避免分散式架構下的雙寫衝突。

## 二、 營運訂單分類與優先權 (Order Category & Priority)

系統定義標準業務優先權矩陣，**數字越大優先權越高**。當車端收到新任務時，若其優先權大於當前任務，車端必須具備中斷或強制覆寫當下行為的能力。

| 英文代碼 | 中文定義 | 優先權 | 邏輯說明 |
| :--- | :--- | :--- | :--- |
| `FORCED_RECALL` | 強制召回 | **100** | 最高指令。立即中斷當前所有動作，無條件返回指定地點。 |
| `EMERGENCY_RESCUE` | 緊急救援 | **90** | 突發接駁。優先於正線營運，強制插隊執行。 |
| `LINE_OPERATION` | 正線營運 | **50** | 標準載客班次，按表操課。 |
| `DISPATCH_PREP` | 整備調度 | **40** | 充電、洗車等後勤作業。 |
| `PRE_OPERATION` | 出車前測 | **30** | 每日發車前的熱身與自檢路線。 |
| `DEPOT_RETURN` | 收班回廠 | **20** | 常規收班。 |

## 三、 核心命名與代碼規範

為確保跨系統識別一致性，嚴格定義以下 ID 格式：

1. **車輛代號 (`vehicle_code`)**: `PMS` + 兩碼數字。(例：`PMS01` ~ `PMS11`)。
2. **班次代碼 (`trip_code`)**: 班次模板識別碼，格式為 `[路線代號][HHMM]`——路線代號取自營運班表的路線設定，`HHMM` 為該班次的發車時刻。(例：`TN1030` 表示 TN 路線 10:30 發車的班次，`NT2135` 表示 NT 路線 21:35 發車的班次)。
   > 早期版本曾定義為 `[方向][時間]`（`U1030`／`D2135`）。方向式代號無法對應到營運班表上的具體路線，車輛即時 ETA 介面因此接不上計畫值。現行規則與班表、[班表與到站預測介面](班表與到站預測介面.md) §2.2 一致。
3. **實體訂單 (`order_id`)**: `[YYMMDD]-[trip_code]`。(例：`260422-TN1030`)。
4. **任務代號 (`task_id`)**: `[order_id]_[task_name]_[sequence]`。(例：`260422-TN1030_OPEN_N2W_02`)。
5. **命名約定**: 所有狀態碼、任務名稱與動作，強制使用 `SCREAMING_SNAKE_CASE`。

## 四、 交互流程與 API 使用說明 (Interaction Workflow)

### 階段一：訂單指派與啟動 (Assignment & Initialization)

1. **【車輛監控系統端】建立訂單 (REST)**：`POST /syncdrive-api/order/save`。狀態設為 `PENDING`。
2. **【車輛監控系統端】觸發發車與優先權宣告 (MQTT)**：
    * **Topic**: `v1/vtms/{vehicle_code}/operation/assign`
    * **Payload**: 
    ```json
    { 
     "vehicle_code": "PMS05", 
     "timestamp": 1713752700000, 
     "order_id": "260422-TN1030", 
     "priority_level": 50 
    }
    ```
3. **【車端】拉取任務與確認啟動 (REST)**：
    * **API**: `GET /syncdrive-api/order/queryById?id=260422-TN1030`
    * **API**: `PUT /syncdrive-api/order/updateOrderProgress/260422-TN1030?status=PROCESSING`。

### 階段二：營運執行與節點任務觸發 (Execution & Node Tasks)

4. **【車端】持續推送營運狀態 (MQTT)**：
    * **Topic**: `v1/vtms/{vehicle_code}/operation/update` (1Hz)。
5. **【車端】節點任務執行 (Node-based Tasks)**：
    * **動作與邏輯**：車輛根據自駕系統的移動位置，當抵達地圖編輯器定義之特定 **點位 (Node)** 時，觸發對應的微觀任務（如語音、開門）。
    * **路口路權不在此列**：請求與取得路權由車端與 SCADA（號誌系統）直接完成，屬車端內部處理，不進 `task_group`。車輛正在等待路權時，以事件 `INTERLOCK_REQ` 告知車輛監控系統端供圖台顯示（見[動態控制與特殊事件協議](動態控制與特殊事件協議.md) §四.5）。

### 階段三：結案與異常恢復 (Completion & Recovery)

6. **【車端】回報訂單結束 (REST)**：`PUT /syncdrive-api/order/updateOrderProgress/260422-TN1030?status=END`。
7. **【系統/人工】異常恢復路徑**：當進入 `FAULTED` 狀態後，需透過 REST API 或實體按鈕重置。

    "target_station_id": "t3_u",

      "task_id": "260422-TN1030_DEPART_02",

## 六、 欄位字典與業務邏輯實作指南

### 1. 任務行為名稱字典 (`task_name`)
本清單對應地圖編輯器中的節點屬性，定義車輛於特定點位應執行之動作：

| 任務代碼 | 說明 | 觸發時機 |
| :--- | :--- | :--- |
| `PRE_DEPARTURE_BROADCAST` | 發車前語音 | 於起始站點準備起步前（剩餘距離達門檻或語音節點）。 |
| `CLOSE_DOORS` | 關門 | 站點停靠結束，準備起步前（車速為 0、距離目標站 ≤ 門檻）。 |
| `STATION_DEPARTURE` | 發車出站 | 車體完全離開站體範圍節點。 |
| `PLATFORM_DOCKING` | 精準對位停靠 | 抵達最終停車目標節點（`current_leg.distance_to_target_m` 進入停靠門檻）。 |
| `OPEN_DOORS` | 開門 | 停靠完成且車速為 0（距離目標站 ≤ 門檻）。 |

**本字典為封閉集合，車端不得自行擴充。**新增任務名稱須先修訂本文件。

> **備註 1**：進站減速由自動駕駛自行處理，不另設 `STATION_ARRIVAL` 任務；進站圖示以 `PLATFORM_DOCKING` IN_PROGRESS 表示。
>
> **備註 2（2026-09-08 修訂）**：原字典另有 `ACQUIRE_INTERLOCK`、`CROSS_INTERSECTION`、
> `RELEASE_INTERLOCK` 三項，已移除。路口通行是車端與 SCADA 之間的內部處理流程，
> 逐項回報會把車端內部狀態機綁進營運介面，也會把程式邏輯的細節推給營運人員設定。
> 車輛等待路權時以事件 `INTERLOCK_REQ` 顯示即可。
>
> 若某個內部流程確實需要車端回報，改由車輛監控系統端逐案開 **action**
> （`PUT /syncdrive-api/order/action/{actionId}`，見[車端介接說明書](車端介接說明書.md) §5.3），
> 車端回報該 action 完成即可——車輛監控系統端決定要看多細，字典不動。

### 2. 微觀任務群組欄位說明
| JSON 欄位 | 型別 | 說明 |
| :--- | :--- | :--- |
| `task_params` | Object | **節點對應參數**。必須包含執行此任務的 `node_id`。 |
| `status` | String | `PENDING` (未抵達節點)<br>`IN_PROGRESS` (抵達節點，執行中)<br>`COMPLETED` (已完成)<br>`FAILED` (失敗/卡關) |
| `actual_start_time` | Long | 抵達節點開始執行之 Unix Epoch (ms)。 |
| `note` | String | 若任務卡在 `IN_PROGRESS` (如：等紅燈) 或 `FAILED`，需填入原因。 |

### 3. `current_leg` 欄位說明

| JSON 欄位 | 型別 | 說明 |
| :--- | :--- | :--- |
| `target_station_id` | String | **必須使用停靠點識別碼**（例如 `t3_u`、`t3_d`，完整清單見 T3 地圖站點與路線清單），不是站名或站體代號。<br>車輛監控系統端以此欄位對應到營運班表的站序與計畫時刻；填 `T3` 這類站體名稱會對不上，因為同一個站體有上行與下行兩個不同的停靠點。清單見 [班表與到站預測介面](班表與到站預測介面.md) §2.5。 |
| `distance_to_target_m` | Double | 距目標停靠點的路徑距離，公尺。 |
| `eta_seconds` | Int | 距抵達目標停靠點的剩餘秒數，**由車端推算**。車輛監控系統端不重算，原值透傳至對外的即時 ETA 介面。 |

> `eta_seconds` 與 `distance_to_target_m` 是對外「即將進站／預計到達」的**唯一來源**。
> 車輛監控系統端據此判定 `arrival_state`（門檻：≤ 60 秒或 ≤ 200 公尺為即將進站），
> 並與班表計畫值相減得出誤點秒數。車端的推估品質會直接反映在站端顯示上。
