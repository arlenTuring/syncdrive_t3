# 資料管理保留政策實作

## 資料類別、關聯與保護

| 類別 | 清理資料 | 可信時間 | 關聯處理 | 永久排除 |
|---|---|---|---|---|
| 一般運行歷史 | `vehicle_history_frames` | `received_at` | 重算 `vehicle_history_stream_keys`，新增可依載具區分的 `retention_cleanup` 缺段；區段本身保留供涵蓋判定 | 最新狀態、車輛／地圖／班表主檔、未完成訂單 |
| 歷史降級回放 | 已結束的 `degraded_replay_sessions` 與其 frames | `ended_real`、`received_at` | 先刪 frames 再刪 Session；`degraded_replay_maps` 僅在沒有任何 Session 引用時回收 | `recording` Session、仍引用的地圖與模型快照 |
| 原始遙測歷史 | `telemetry_logs` | 新增的 `received_at` | 只處理有可信接收時間的資料；`vehicle_monitor_demo` 最新快照不在範圍 | 缺少 `received_at` 的舊資料、最新狀態快照 |
| 其他大量紀錄 | 已 ACK 指令、已釋放／拒絕路權、具有接收時間的事件 | `sent_at`、`requested_at`、`received_at` | 各表採有索引、有界批次 DELETE | 未完成指令、持有中路權、操作／權限／資料清理稽核 |

訂單契約、帳號、角色、憑證、車輛註冊、服務設定、啟用地圖、模型、班表及最新快照沒有任何清理入口。清理 API 只接受上述固定類別，不接受資料表名、SQL 或檔案路徑。

## 流程與一致性

1. `POST /syncdrive-api/data-admin/cleanup/preview` 以登入操作者建立 10 分鐘短效計畫，固定 `snapshotAt` 與截止時間，執行精確範圍計數但不刪資料。
2. `POST /cleanup/plans/:id/execute` 重新驗證 Session/CSRF、`system.data-admin.cleanup`、操作者、到期時間及進行中回放／錄製／訂單指紋。相同 plan 只能產生一個工作。
3. 背景工作先沖刷遙測及回放寫入緩衝，以專用 PostgreSQL 連線持有 advisory lock，防止多實例同時清理。
4. 工作以 2,000 筆為批次，每批邊界檢查停止旗標。截止時間固定，執行中新增的資料不會擴大刪除範圍。
5. 後端重啟會把中斷中的工作標成「部分完成」，排隊中的工作會恢復；刪除筆數不會假裝回復。
6. 完成後記錄資料庫容量與後端檔案系統可用空間前後值。一般 DELETE 只保證空間可供 PostgreSQL 重用，不宣稱已縮檔或歸還作業系統。

指定單車或部分區間永不使用 `drop_chunks`。目前 TimescaleDB 的 chunk 維度是車端 `timestamp`，而新政策使用可信 `received_at`；因此無法安全證明整個 chunk 都符合範圍，本版不呼叫 `drop_chunks`。若未來要立即回收 chunk，應將新表／新 hypertable 的分區時間改為後端接收時間，不能用車端或模擬時鐘替代。

## 權限與 API

| 權限 | API |
|---|---|
| `system.data-admin.view` | 容量概況、類別、政策與工作紀錄 |
| `system.data-admin.cleanup` | 清理預覽、執行、停止 |
| `system.data-admin.policy` | 政策影響預覽、儲存政策 |
| `system.data-admin.execute` | 保留原有 SQL／即時資料重置功能 |

前端不再用 `X-Syncdrive-Role` 當授權依據；所有修改走既有 Cookie Session、CSRF 與 `AccessGuard`。操作權限不足時按鈕仍顯示，點擊統一顯示「權限不足」。

## 自動政策

- Migration 只建立四筆 `enabled=false` 的設定，不啟用任何新刪除。
- 已存在的 TimescaleDB telemetry retention job 會顯示成外部管理；系統不重複排程，也不自動縮短或移除。
- 啟用或縮短保留期限必須先做影響預覽，再用同一操作者的未過期計畫確認。
- 排程使用後端 `Date.now()` 和資料的可信接收／保存時間，與模擬營運時鐘、車端 timestamp 無關。

## 部署與回復

1. 備份資料庫結構（不必為每次清理複製整份歷史資料）。
2. 執行 `backend/src/database/migrations/20261015-data-retention-management.sql`；可重複執行。
3. 部署後端及前端，確認 `/retention/overview` 回 200、四筆新政策仍為停用。
4. 由管理員在介面預覽後自行啟用需要的政策。

回復應先在介面停用政策並等待目前批次邊界停止，再回退應用版本。三張 `data_*` 管理表與新增欄位可保留，不影響舊版；不要為回版刪除稽核紀錄。已完成的資料刪除不可由回版復原，需使用部署前由使用者自行保留的備份。
