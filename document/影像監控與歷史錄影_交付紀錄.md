# 影像監控與歷史錄影：交付紀錄

依據：`document/影像監控標籤頁與歷史錄影_Claude_Code實作指示.md`（覆蓋事件管理指示中影像的部分）。
本文件是工程交付紀錄；尚未實機驗證的項目列在第八節，不放在使用者畫面。

## 一 架構

```
攝影機（RTSP／RTSPS／RTMP／HLS／SRT）
   │  只允許「影像連線範圍」內的位址；DNS 解析後鎖定 IP，擋 loopback／metadata／link-local
   ▼
MediaMTX 1.21.2（固定 digest）── 分段錄影 fMP4 ──► 錄影 volume ──► GCS（選用）
   │ Control API v3（docker 網路內）         ▲ hook：片段完成通知後端建立索引
   ▼                                          │
後端 API（VIDEO_ROLE=api）                   媒體 worker（VIDEO_ROLE=worker，獨立容器）
  ・設定、權限、播放授權（短效權杖綁 Session）   ・設定同步（advisory lock，單一執行者）
  ・HLS／WHEP 代理、歷史 manifest              ・索引補漏、保存與容量回收
  ・片段由 nginx X-Accel-Redirect 送檔          ・GCS 上傳、背景壓縮、下載工作（SKIP LOCKED）
   ▼
瀏覽器：WebRTC 優先，5 秒內無畫面改 HLS；歷史以絕對時間同步多來源
```

- 來源每次改連線就產生新 revision，各自有媒體路徑 `vs_<revisionId>`；舊歷史以 revision 查得到，換鏡頭不會把舊車畫面掛到新車。
- 同一來源被多格使用只接入、只錄一份；任一格要求錄影即錄影。
- 錄影是伺服器端行為：關網頁、登出都不影響；worker 重啟依資料庫的需求恢復。
- 錄影原碼流，不重新編碼（`recordingProfile=original`）。

## 四 API

全部在 `/syncdrive-api/video`，Swagger 標籤「影像監控」。

- 設定：`GET bootstrap`；`GET/POST tabs`、`PATCH/DELETE tabs/:id`、`POST tabs/reorder`、`POST tabs/:id/duplicate`、`GET tabs/:id/tile-count-preview`、`PUT tabs/:id/tiles`；`GET/PUT defaults`、`POST defaults/preview-apply`、`POST defaults/apply`；`GET/PUT settings`。
- 來源：`GET/POST sources`、`GET/PATCH/DELETE sources/:id`；`POST/GET/DELETE source-tests[/:id]`；`POST sources/:id/live-sessions`。
- 儲存：`GET storage-status`、`GET/PUT storage-policy`、`GET capabilities`。
- 歷史：`GET recordings/availability|calendar|recordings`；`POST playback-sessions`；`POST exports`、`GET jobs/:id`；`POST recordings/delete-preview|deletions|protect`。
- 不需登入但需權杖（權杖綁登入 Session，每次請求重新檢查）：`GET playback/:token/manifest`、`GET playback/:token/segments/:id`、`GET exports/:token/:name`、`/video/live/:token/*`（HLS 與 WHEP 代理）。
- 內部：`GET internal/segment-complete`（只給媒體服務，需 `X-Video-Hook-Secret`；nginx 對外一律 404）。

回應與稽核都不含來源密碼；網址一律遮罩（`rtsp://cam:***@…`）。

## 六 編碼策略實測比較

合成畫面（testsrc2，1080p 15 fps，60 秒，H.264 約 4 Mbps 為原檔），本機 8 核 CPU，ffmpeg 以 `nice 19` 執行，VMAF 為成品對原檔：

| 策略 | 編碼器與參數 | 檔案 | 節省 | VMAF | 編碼耗時 |
| --- | --- | --- | --- | --- | --- |
| 原檔 | H.264（攝影機原碼流） | 30.1 MB | — | — | — |
| AV1 | libsvtav1 preset 8、crf 35 | 17.4 MB | 42.3% | 96.6 | 41 秒（約 0.7 倍即時） |
| HEVC | libx265 medium、crf 28、hvc1 | 24.6 MB | 18.3% | 95.9 | 37 秒 |
| H.264 重編 | libx264 medium、crf 23 | 27.3 MB | 9.4% | 97.7 | 12 秒 |

720p 20 秒片段（約 2 Mbps）：AV1 省 42.4%、VMAF 98.0；HEVC 省 26.6%、VMAF 96.9。

結論與限制：

- AV1 省最多，但 CPU 最重。一路 1080p 需要約 0.7 倍即時的單機 CPU 時間；多路持續錄影時，背景壓縮可能追不上新錄影。並行數與 worker CPU 上限要依實際路數調整。
- HEVC 節省較少，但 Safari／Edge 的播放相容性較好。
- 合成畫面比真實監視畫面容易壓縮，數字不能直接套用到現場。啟用前要用現場錄影各取一段，人工比對後再定門檻。
- 預設門檻：節省 ≥15%、VMAF ≥90、時長差 ≤0.5 秒。VMAF 高分不等於取證畫質合格，所以預設保留原檔。

## 七 部署步驟（GCP 或現場主機）

1. 推上 `main` 後執行 `./deploy/sync.sh`（流程不變）。Migration 會列出 `20261023-video-monitoring.sql`。
2. 同步時自動補齊 `deploy/.env` 的影像密鑰，包括 `VIDEO_MEDIAMTX_PASSWORD`、`VIDEO_PUBLISH_PASSWORD`、`VIDEO_HOOK_SECRET` 與 `VIDEO_SECRET_KEY`：
   - 只補缺的值，不覆寫已有的值。
   - `VIDEO_WEBRTC_PUBLIC_HOST` 預設等於 `MQTT_PUBLIC_HOST`。
   - `VIDEO_SECRET_KEY` 用來加密來源密碼，產生後不要更換，也不要遺失。
3. 同步會啟動 `mediamtx` 與 `video-worker`：
   - 錄影存在 `videorecordings` volume，刻意不放在 `/app/data` 底下，避免被同步備份整包複製。
   - 下載暫存檔放在 `videoexports`。
4. 防火牆（GCP VPC）需開 UDP 8189 給使用者網段，WebRTC 才連得上。沒開也能用，播放器會改走 HLS，延遲較高。
5. 最高管理員登入後，到角色管理勾選第三節的權限。
6. 到「影像監控」的設定加入攝影機：
   - 先在「影像連線範圍」確認攝影機網段（預設 10.0.0.0/8、192.168.0.0/16）。
   - 再用「測試連線」確認畫面。
7. 確認錄影儲存設定。
   - 預設：保留 7 天，預算取 50 GiB 與可用空間 25% 的較小者。
   - 要用 GCS 時：VM 服務帳號需要該 bucket 的 `storage.objects.create/get/delete` 權限，以及 `storage.buckets.get` 權限（用來讀取 soft delete 設定）。
8. 健康檢查新增 4 項：
   - 媒體服務在線且帳密正確。
   - worker 執行中。
   - 錄影空間可寫。
   - hook 不可從外部打到。

9. 背景壓縮預設關閉。要開啟時，在「錄影儲存設定 → 進階」勾選，並選 AV1 或 HEVC；設定頁會依主機實際偵測的編碼器與 VMAF 工具決定能不能勾。
10. 在 GCP 上跑整合測試（只在測試期間做；測試會暫時改動儲存政策，結束自動還原）：

```bash
sudo ./scripts/video-test-cameras.sh start 2 1800
sudo docker exec -e VIDEO_ITEST_ALLOW=1 syncdrive_video_worker node scripts/video-itest/verify-video.cjs <主機內網 IP>
sudo docker exec -e VIDEO_ITEST_ALLOW=1 syncdrive_video_worker node scripts/video-itest/verify-recording.cjs <主機內網 IP>
sudo docker exec -e VIDEO_ITEST_ALLOW=1 syncdrive_video_worker node scripts/video-itest/verify-archive.cjs
sudo ./scripts/video-test-cameras.sh stop
```

   - 測試攝影機在主機的 18554 埠，主機上沒有 ffmpeg 時改在攝影機容器內推流；GCP 防火牆不要對外開 18554。
   - 主機內網 IP（10.x）需在「影像連線範圍」內（預設已含 10.0.0.0/8）。
   - 錄影分段在正式環境是 60 秒，錄影測試要等兩段完成，最多約 2–3 分鐘。

回退：
- `sync.sh` 回復舊版時，只啟動舊版 compose 裡有的服務，並停止媒體 worker。
- 影像資料表是新增的，回退不需要刪除。

## 八 尚未驗證

- 真實攝影機：目前只用過合成串流。廠牌 RTSP 細節（Digest 變體、主／子碼流、H.265 來源）未實測。
- 12 路、≥10 Hz 驗收：本機只跑 2 路合成串流。需在目標主機用 11／12 路實際來源量測 fps、丟幀、CPU 與首幀時間（p50／p95）。
- 瀏覽器：只在 Chrome 系驗證 API 層，Safari／Edge 實際播放（含 HEVC 成品）未測。畫面操作需使用者登入後進行。
- GCP WebRTC ICE 路徑：未在 GCP 實測。沒有 TURN，NAT 不通時靠 HLS 備援。
- GCS：本機沒有 GCP 服務身分。上傳、md5 驗證、generation、ranged 讀取、soft delete 顯示都只驗到「無身分時明確報錯」，需在 GCP 以測試 bucket 驗證，不可用正式 bucket 做破壞性測試。
- 轉碼 proxy：H.265／AV1 來源目前只錄原碼流，沒有產生共用的 H.264 相容 proxy；瀏覽器不支援時歷史片段會顯示「無法播放」。原始／平衡／節省空間三種即時轉碼預設尚未實作，`recordingProfile` 目前只有 `original`。
- 只在雲端的片段無法快速下載：下載由媒體服務讀本機原檔。區間內有片段只在雲端或已被壓縮版取代時，建立下載就會被拒絕並說明原因（仍可直接播放）。
- 影像與軌跡對齊誤差（目標 ≤500 ms）：需要車上真實攝影機與時間戳才能量測。
