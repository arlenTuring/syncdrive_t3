# 舊訂單資料檢查與升級（2026-10-05 整合版）

整合分支 `integration/order-lifecycle-2026-10-05` 改了幾條規則：

- 車次代號（D1234、NT0000…）不再決定業務分類、開始執行、是否顯示、計畫時刻。
- 訂單開始與結案只認車端 REST `updateOrderProgress`。MQTT `vehicle_phase=FAULTED`、`CRITICAL` 事件只標記「車輛故障，訂單結案待確認」，不替車端結案。
- 模擬執行追蹤用 `plan_run_id`、`plan_shift_id`、`plan_load_digest`、`plan_run_total`。

新程式碼不會自動改舊資料，也不會猜。上 GCP 之前，先用唯讀查詢看舊資料受影響的範圍。**這份說明不在 GCP 上執行任何寫入。**

## 一、唯讀檢查

查詢檔：`backend/scripts/sql/check-legacy-orders.sql`。檔案開頭有 `SET default_transaction_read_only = on`，整個連線都是唯讀，就算誤貼 `UPDATE`，資料庫也會直接拒絕（本機已驗證：`cannot execute UPDATE in a read-only transaction`）。

在已登入 gcloud 的 Mac、整合分支目錄執行（VM 上的程式碼還沒有這個檔，所以把本機檔案從標準輸入送進去）：

```bash
gcloud compute ssh syncdrive-t3 --zone asia-east1-a --command "sudo docker exec -i syncdrive_postgres sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -v ON_ERROR_STOP=1'" < backend/scripts/sql/check-legacy-orders.sql
```

| 檢查 | 代表什麼 | 新版畫面的影響 |
|---|---|---|
| 1 `unclassified` | `line_kind` 空白，payload 也沒有 kind／task_type | 班次運行紀錄兩個分頁、班次卡都不列。舊版會靠 D/U 代號把一部分擠進正線分頁 |
| 2 `missing_planned_time` | 沒有 planned_start／planned_end | 發車／結束時間顯示「—」，不再從代號推 |
| 3 `pending_but_vehicle_moving` | 待發中，但車端報行駛／停靠 | 舊版 D/U 單會被 MQTT 直接改成執行中；新版要等車端 REST 回報開始 |
| 4 `open_unsourced_du_mainline` | 沒結束、沒來源標記的正線 D/U 單 | 舊版後端示範會依代號把它們結束；新版不會 |
| 5 `faulted_by_mqtt_rule` | 舊規則由 MQTT／事件直接結案的 FAULTED | 只供了解，不需要改 |
| 6 `plan_replay_tracking` | 模擬器重播單有沒有 `plan_run_total` | 沒有的舊輪次，追蹤 API 回 `plan_size_unknown`，不宣稱完成 |
| 7 `vehicle_fault_pending` | 目前「車輛故障，結案待確認」的單 | 上線後才會出現，車端 REST 結案後就消失 |

本機（2026-10-05）的結果：1、2、4、5 都是 0 筆；3 只有本次驗收建的 2 張 PMS99 測試單；6 有 1942 張舊重播單沒有 `plan_run_total`，都已經結束。

## 二、需要升級時怎麼做（GCP 上要先另外確認、先備份）

原則：只用訂單上**已經記錄的資料**補值，不從車次代號推；補不了的就列出來人工決定。每一步都先跑預覽 SELECT，確認筆數再寫。

1. **先備份**：

   ```sql
   CREATE TABLE operation_orders_backup_20261005 AS TABLE operation_orders;
   ```

2. **分類不明（檢查 1）**：
   - 有 `payload.kind`／`task_type` 的單，新程式已經自動換算，不用改。
   - 兩者都沒有的單，看 `payload.source` 與建立來源，人工決定 `line_kind`，再用明確的 order_id 清單更新：

     ```sql
     UPDATE operation_orders SET line_kind = 'MAINLINE' WHERE order_id IN (...);
     ```

     **不要**寫成 `WHERE trip_code ~ '^[DU]'`。
   - 舊模擬器的 TEST 重播單：用 `backend/scripts/reclassify-plan-replay-orders.js`。預設只預覽，`--apply` 才寫入；它依單上的 `plan_shift_id` 重新查班表，只有對得上的才改。

3. **缺計畫時刻（檢查 2）**：只補 payload 裡有調度引擎記錄的那些：

   ```sql
   -- 預覽
   SELECT order_id, payload->>'planned_depart_at', payload->>'planned_arrive_at'
   FROM operation_orders
   WHERE planned_start IS NULL AND payload ? 'planned_depart_at';
   -- 寫入
   UPDATE operation_orders
   SET planned_start = (payload->>'planned_depart_at')::bigint,
       planned_end   = COALESCE(planned_end, (payload->>'planned_arrive_at')::bigint)
   WHERE planned_start IS NULL AND payload ? 'planned_depart_at';
   ```

   沒有這兩個欄位的單維持空白，畫面顯示「—」。

4. **待發但車端已在跑（檢查 3）**：這是車端沒照協議先用 REST 回報開始。請車端補呼叫 `updateOrderProgress?status=PROCESSING`；中心端不要直接改狀態。

5. **沒來源標記、還沒結束的 D/U 正線單（檢查 4）**：確認是殘留單之後，用中心端取消 API（`PUT /syncdrive-api/order/cancel/{id}`）走正常結案，不要直接改成 END。

6. **模擬執行追蹤（檢查 6）**：舊輪次沒有 `plan_run_total`，維持「計畫數未知」就好，不補值。新一輪由新版模擬器建單就會有。

## 三、相容期限

- 不保留 `sim_run_id`／`sim_shift_id`／`sim_load_digest` 別名：查過本機資料，沒有任何訂單用過這組名稱（#13 從未合併）。
- 沒有 `plan_run_total` 的舊重播單，追蹤 API 會一直回報「計畫數未知」。這不是錯誤，不設期限，也不需要轉換。

## 四、告警 `event_id` 撞號：部署前的 migration

`security_event_logs` 的主鍵從車端 `event_id` 改成內部 `id`（理由與去重規則見 `security-event-log.entity.ts` 的 `securityEventDedupKey`，以及動態控制與特殊事件協議 §四 的補充）。

正式環境開著 `DB_SYNCHRONIZE=true`，新版後端啟動時也會調整成相同結構，但**不會回填舊資料的去重鍵**，也不會先備份。所以部署新版之前，先在 GCP 執行（會先建立備份表 `security_event_logs_backup_20261005`，不刪任何資料，可以重複執行）：

```bash
gcloud compute ssh syncdrive-t3 --zone asia-east1-a --command "sudo docker exec -i syncdrive_postgres sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -v ON_ERROR_STOP=1'" < backend/scripts/sql/migrate-20261005-security-event-log-identity.sql
```

最後一段核對查詢：`rows_now` 應等於 `rows_backup`，`missing_dedup_key` 應為 0。這支 migration 已在本機兩種狀態驗證過：舊結構（`event_id` 為主鍵）、已被 synchronize 改過的新結構。

## 五、同一張單的並行寫入：目前是單一實例

已查過的部署設定：

- 正式環境：`deploy/docker-compose.prod.yml` 的後端寫死 `container_name: syncdrive_backend`，這樣無法擴成多份；沒有 replicas、cluster 或 PM2；Docker 直接執行 `node dist/main.js`。
- 本機：`scripts/dev-start.sh` 只啟動一個 `nest start --watch`。

所以目前用 `OrderService` 程序內依訂單 ID 排隊保護就夠了：MQTT 進度、REST 開始／結束／故障、中心端取消、動作回報、CRITICAL 事件標記，以及非重播單的建單覆寫，全部經過同一個排隊，進入後重新讀取，狀態轉換照 VALID_TRANSITIONS 檢查。另外：

- 已開始、已結案或已取消的單，不能再用建單覆寫（409 `ORDER_NOT_OVERWRITABLE`）。
- 後端示範（`payload.source='backend_demo'`）自己的對帳不經過排隊，只動示範自己建的單。

**啟用多實例之前必須做的事（本輪不做）：**

1. 訂單狀態轉換改成資料庫條件更新：`UPDATE ... WHERE order_id = $1 AND status = $舊狀態`，或在交易裡 `SELECT ... FOR UPDATE`。
2. payload 改成原子合併：`payload = payload || $patch`，取代讀出整包再寫回。
3. 建單覆寫改成 `INSERT ... ON CONFLICT DO UPDATE ... WHERE status = 'PENDING' AND NOT payload ? 'cancel_requested_at'`。
4. 示範對帳也要套用同樣的條件。
5. 拿掉程序內排隊之前，先用兩個實例重跑 `order.service.spec.ts` 裡的並行測試情境。
