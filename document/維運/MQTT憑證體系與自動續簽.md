# MQTT 憑證體系與自動續簽

> 內部文件。對外只需要知道「每天呼叫一次取得憑據」，見[協力廠商介接說明書](../對外介接/協力廠商介接說明書.md) §1.3。

| 項目 | 內容 |
|------|------|
| 適用範圍 | MQTT 8883 的 TLS 雙向驗證憑證 |
| 自動化程度 | 全自動。除了首次建立，不需要任何人為操作 |
| 觸發方式 | systemd timer `mqtt-certs.timer`，每日 03:20（UTC） |

---

## 一、為什麼要有這份文件

憑證到期是最安靜的一種故障：到期那天之前一切正常，之後全部連不上，而原因與任何一次程式改動都無關。查的人會先去看最近的 commit，然後看設定檔，最後才想到憑證——那時已經停擺好幾個小時。

原本的設計正是如此。`deploy/mqtt-certs.sh` 的邏輯是「憑證已存在就沿用」，也就是**永遠不會續簽**，只是把停擺排程到 2028 年（伺服器憑證）、2031 年（中介）與 2036 年（根）。

現在改成每天檢查、提前續簽，而且續簽的過程要在車端每天重新取得憑據的節奏下無感完成。

---

## 二、憑證體系

```
根 CA（自簽，10 年）
├── 伺服器憑證（825 日）      broker 的身分，證明「我是 34.80.84.224」
└── 中介 CA（5 年）
     └── 車輛憑證（24 小時）   每台車一張，證明「我是 PMS01」
```

### 2.1 為什麼分兩層

車輛憑證改成申請當下即時簽發之後，後端必須握有一把能簽出任何車輛身分的私鑰。

若那把是根 CA 的私鑰，後端一旦被攻破，攻擊者不只能冒充任何一台車，還能簽出伺服器憑證冒充 broker——中間人就成立了。

所以簽車輛的權力下放給中介：

| 私鑰 | 權限 | 檔案權限 | 誰讀得到 |
|------|------|----------|----------|
| `ca.key` | 簽中介與伺服器憑證 | `600 root` | 只有主機的 root，容器內讀不到 |
| `client-ca.key` | 只簽車輛憑證 | `640` 群組 gid 1000 | 後端容器（唯讀掛載） |
| `server.key` | broker 自己的身分 | `600` uid 1883 | 只有 mosquitto |

後端被攻破的後果因此縮小到「能冒充車輛」，冒充不了 broker；而且撤銷中介、換一把重簽即可，不必動到根與所有車端已知的信任錨點。

### 2.2 檔案

位於 `mosquitto/certs/`：

| 檔案 | 內容 |
|------|------|
| `ca.key` / `ca.crt` | 現行根 |
| `ca-next.key` / `ca-next.crt` | 接班根，只在換根過渡期間存在 |
| `ca-published.crt` | **發給車端的信任錨點**：現行根、接班根、尚未過期的舊根 |
| `client-ca.key` / `client-ca.crt` | 現行中介 |
| `ca-chain.crt` | **broker 的 `cafile`**：所有仍有效的根與中介 |
| `server.key` / `server.crt` | broker 的身分 |
| `retired/` | 已退役但尚未過期的根與中介，過期後自動刪除 |
| `.changed` | 憑證有變動的記號，由 renew 腳本消費 |

`ca-published.crt` 與 `ca-chain.crt` 是兩個不同方向的信任集合，不要混用：

- `ca-published.crt` 給**車端驗 broker**，只含根。
- `ca-chain.crt` 給 **broker 驗車端**，含根與所有中介。

## 三、自動續簽

### 3.1 每天發生什麼

`mqtt-certs.timer` 於每日 03:20 觸發 `mqtt-certs.service`，執行 `deploy/mqtt-certs-renew.sh`：

1. 從 `deploy/.env` 的 `MQTT_PUBLIC_HOST` 取得主機位址（讀不到就問 GCP metadata）。
2. 執行 `deploy/mqtt-certs.sh <位址>`。這支是冪等的，沒有東西快到期就什麼都不做。
3. 若憑證真的變了（`.changed` 存在），重建 mosquitto 容器，然後清除記號。

絕大多數日子第 3 步不會發生。**沒有變動就不重建**是刻意的——每天無謂地重建會讓所有車端斷線重連，那本身就是一種停擺。

### 3.2 三張憑證的續簽時機與影響

| 憑證 | 續簽門檻 | 車端受到的影響 |
|------|----------|---------------|
| 伺服器憑證 | 剩 90 天 | 無。車端不持有它，只驗證它是不是根簽的 |
| 中介 CA | 剩 365 天 | 無。舊中介留在 `ca-chain.crt` 直到過期，已發出的車輛憑證仍然有效 |
| 根 CA | 剩 3 年開始，分兩階段 | 無。見 §3.3 |

門檻都遠大於車端一天一次的換發週期，留足反應時間。

門檻可用環境變數覆寫（`SERVER_RENEW_AT`、`INTERMEDIATE_RENEW_AT`、`ROOT_PREPARE_AT`、`ROOT_CUTOVER_AFTER_DAYS`），供測試把時間快轉用。正式環境不要設定這些變數。

### 3.3 換根為什麼要分兩階段

根是**唯一車端必須事先信任**的東西。若當場換掉，昨天取得憑據的車端只認舊根，會驗不過 broker 的新憑證而集體斷線。

所以：

| 階段 | 觸發 | 做什麼 |
|------|------|--------|
| 一、公布 | 根剩 3 年 | 產生 `ca-next`，加進 `ca-published.crt`。**不動現行根，不重簽任何東西** |
| 二、切換 | 接班根公布滿 30 天 | 接班根成為現行根，中介與伺服器憑證改由它簽發。舊根移入 `retired/`，留在兩個信任集合中直到過期 |

30 天的重疊期遠大於車端一天一次的換發週期。重疊期間取得憑據的車端，信任錨點裡同時有新舊兩把根，切換前後都連得上。

超過 30 天沒有更新憑據的車端會在切換後連不上——這是設計上的取捨，而不是缺陷：它的 API 金鑰在第一天就已經過期了。

## 四、後端如何跟上

後端在申請憑據時當場簽發車輛憑證，所以它也要跟著換：

| 檔案 | 後端怎麼處理 |
|------|-------------|
| `ca-published.crt` | 每次申請都重讀，直接放進回應的 `mqtt.ca_certificate` |
| `client-ca.crt` | 每次申請都重讀，放進 `mqtt.intermediate_certificate` |
| `client-ca.key` | 解析後快取，但**比對檔案 mtime**，變了就重讀 |

中介私鑰要快取是因為解析 PEM 每次幾十毫秒，一次申請要簽十一張。但不能永久快取：中介每年會被續簽換掉，若還拿著舊的那把私鑰，簽出來的車輛憑證就與同一包裡交付的 `intermediate_certificate`（讀檔案，永遠是新的）對不起來。

這個問題的症狀會延遲好幾年才出現——舊中介還在 `ca-chain.crt` 裡，連線照常，要等舊中介真的過期才變成連不上，那時已經沒有人記得這裡有快取。

**後端不需要重啟**。憑證目錄是以目錄形式掛載的（不是逐檔掛載），所以續簽時無論是原地覆寫還是換檔案，容器內都看得到新內容。

## 五、萬一自動化本身壞了

自動化會壞：timer 沒啟用、腳本執行失敗、續簽了卻沒重建 broker。所以 `deploy/healthcheck.sh` 直接檢查**正在服役的那幾張憑證**還剩多久：

```
憑證效期
  ✓ broker 伺服器憑證          剩 824 天
  ✓ 中介 CA（簽車輛憑證用）     剩 1824 天
  ✓ 根 CA                     剩 3649 天
```

紅線是 30 天（可用 `CERT_MIN_DAYS` 調整），任一張低於它整份驗收就失敗。續簽門檻是 90 與 365 天，掉到 30 天代表自動續簽已經連續失敗一段時間，而距離真正停擺還有一個月可以處理。

### 5.1 手動處理

```bash
sudo systemctl status mqtt-certs.timer
```

```bash
sudo journalctl -u mqtt-certs.service -n 50
```

手動觸發一次續簽：

```bash
sudo /opt/syncdrive_t3/deploy/mqtt-certs-renew.sh
```

## 六、驗證

`deploy/test-cert-rotation.sh` 用真的 mosquitto 與真的 TLS 連線，把續簽門檻調到必定觸發，讓整條輪替在幾分鐘內依序發生。輪替一次要好幾年，沒有辦法用等的方式驗證。

```bash
sudo ./deploy/test-cert-rotation.sh
```

模擬的客戶端只做協力廠商該做的兩件事：取得憑據、連線。每一步分別測試「已持有舊憑據的客戶端」與「剛重新取得憑據的客戶端」——輪替真正的風險是前者，它在車輛監控系統端換憑證的那一刻正連著線。

14 項檢查涵蓋：

- 首次取得憑據即可連線、無憑證被拒
- 伺服器憑證續簽後，已持有舊憑據的客戶端不受影響
- 中介續簽後，舊中介簽出的車輛憑證仍然有效
- 換根階段一時現行根未變動，新取得的錨點含新舊兩把根
- 換根階段二後，重疊期間取得憑據的客戶端仍連得上
- 超過重疊期未更新的憑據如設計失效
- 沒有變動的日子不會重建 broker

## 七、注意事項

### 7.1 換憑證後 broker 必須重建，不是重啟

mosquitto 的憑證是以 bind mount 掛進去的，綁的是掛載當時解析到的目錄。若憑證是整套重建（例如把 `certs` 改名再產生一份新的），容器裡看到的仍然是舊目錄的內容，broker 會繼續送舊憑證，而且**完全沒有錯誤訊息**。

實測遇過一次：憑證換好了，`openssl s_client` 顯示 broker 送出的仍是上一代的 CA。`mqtt-certs-renew.sh` 已經處理這件事，手動操作時要記得。

### 7.2 首次建立

新機器上第一次執行：

```bash
sudo /opt/syncdrive_t3/deploy/mqtt-certs.sh 34.80.84.224
```

之後掛上 timer：

```bash
sudo cp /opt/syncdrive_t3/deploy/systemd/mqtt-certs.* /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now mqtt-certs.timer
```

### 7.3 根私鑰應該離線保存

`ca.key` 目前留在主機上，`600 root`。它簽完中介與伺服器憑證之後就沒有日常用途——只有換根的那兩次會用到。正式營運環境應該把它搬離這台機器，換根時再帶回來。

搬走之後自動續簽會失效（伺服器與中介都要根來簽），所以那是一個需要一併設計流程的改動，不是單純把檔案移走。
