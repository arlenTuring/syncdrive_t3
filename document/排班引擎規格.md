## 1. 引擎要解決什麼

把 Wizard 已確認的四類輸入編成一張可執行的正線班表：

| 輸入 | 來源 | 引擎怎麼用 |
|------|------|------------|
| 時間模板 | Step 3 | 營運時段、班距、時間線列數、正線可用視窗、整備／充電等非正線視窗 |
| 整備任務 | Step 2 | 非正線占用參數；各整備區段的正線優先讓渡餘裕在**建立班表 Step 2**設定（預設 600s），不寫入整備任務本體 |
| 時間模板 | Step 3 | 若全日有未排定時間屬性的空時段，於建立班表 Step 3 設定「空時段正線讓渡餘裕」（預設 600s） |
| 路線群組 | Step 4 | 執行順序、行駛時間（拓撲 leg 加總優先）、站點停靠、靠站緩衝秒數、換線緩衝、最低恢復時間 |
| 折返時限 | 由模板推導 | 單路線／整輪循環不得超過 |

產出：`GeneratedSchedulePlan`（各時間線區塊）＋可行性報告（errors / warnings）。

## 2. 硬約束一覽（必須同時成立）

### 2.1 占用（S4 靠站緩衝＋S3 對齊）

```
有效平均行駛 = stationLegTravels 完整？ Σ(leg.avg) : 路線 avgTravelTimeSeconds
一趟占用秒數 = snap↑10秒( 有效平均行駛 + Σ (站停 + 靠站緩衝秒數) )
```

靠站時間**含在區塊長度內**，不是兩趟之間的空檔。  
站點時刻（班次卡 hover）：依拓撲 leg 權重分配「班次卡時長 − 停靠」；缺 leg 時均分（見 [點位拓撲規格](點位拓撲規格.md)）。  
**到站時刻**須對齊 10 秒格（例 `00:30:20`、`12:00:10`；`15:37:02` 不行）。為維持班距可比拓撲平均略慢抵達（最多約 1.3× 平均，且至少多 10 秒空間供對齊），但不可低於拓撲最快。

### 2.2 兩趟之間空檔（S1 恢復 ＋ S2 換線）— **相加，不可取 max**

```
同路線連續：
  下一趟發車 ≥ 前趟結束 + 最低恢復時間

換路線（例：下行→上行）：
  下一趟發車 ≥ 前趟結束 + 最低恢復時間 + 前一路線換線緩衝
```

與 Step 4「完整循環」看板一致：恢復與切換是獨立可加項。

**舉證（模擬正線草稿）**

| 參數 | 值 |
|------|-----|
| 平均行駛 | 320 s |
| 三站停靠各加固定緩衝（例：30+10）×3 | 120 s |
| 占用 | 440 s（7 分 20 秒） |
| 恢復 | 30 s |
| 換線緩衝 | 20 s |
| 下行 00:10:00 結束 | 00:17:20 |
| 上行最早發車 | 00:17:20 + 50 s = **00:18:10** |

### 2.3 路線執行順序（硬輪替）

同一時間線上的正線，嚴格依 Step 4 執行順序輪替（下行→上行→…）。  
**不再**為了「可行性」改選其他路線；不可行則寫入該順序並由驗證報錯。  
這保證「一輛車出去必須把路線順序跑完」與週期補完假設一致。

### 2.4 週期補完（來回約束）＋ 同方向班距對齊

識別碼：`rotation-cycle-completion-v1`

除非意外，每輛車（時間線）必須依路線群組執行順序跑完整輪（例：下行→上行）後，才能進整備或收班，以便下一個整備點對應正確的終點站。跨正線視窗時，輪替狀態須推進至下一個完整循環邊界：上一視窗缺回程則補回，無合法回程位置則撤回該輪尚未完成的自動去程，完成後下一視窗才從新一輪開始。不可只暫時把候選方向視為第一條路線而不更新內部輪替計數。

補完失敗或產出仍缺趟時，報告 `ROTATION_CYCLE_INCOMPLETE`。

- 遇到充電／保養／收班前，該車正線趟數必須是路線數的整數倍。
- 不完整則自動補回程。回程發車時刻取**兩者較晚**：
  1. 物理下限：§2.2 公式（前趟結束 + 恢復 + 換線緩衝）。
  2. **同方向班距對齊**：距全車隊上一班**同方向**發車 ≥ 該時段班距。
     不足時往後推到「上一班同方向 + 班距」。
- **上限（產生層必須遵守）**：
  1. 回程必須在「整備開始＋該區段整備切入餘裕」前完成。餘裕限制的是完整回程結束時間，不是只限制發車時間。
  2. 補完後須與同車後續已掛正線留足 §2.2 空檔。
  3. 自動掛出的部分循環若找不到同時滿足班距與空檔的回程，撤回該輪尚未完成的去程；人工固定班次不能自行撤回時才報 `ROTATION_CYCLE_INCOMPLETE`。不得排出 0 秒換線。
- 整備視窗是彈性的：回程可吃進整備開頭；整備**延後開始、鎖住原結束時間並壓縮時長**。只縮短被佔用的那段，不移動其他整備。若後面還有正線錨點，再裁剪整備尾端。**正線優先於整備。**
- 日界保護：自動掛車若無法在 24:00 前完成整輪，撤回尚未成輪的末班去程，不產出必然違規的回程。人工固定班次無法自行撤回時才回報衝突。

**舉證（模擬正線）**：五號列上行 00:20:00 發車、六號列下行 00:17:20 結束。
六號列回程物理最早 00:18:10，但距 00:20 的上行不足 600 秒班距 →
對齊到 **00:30:00** 發車、00:37:20 結束；充電從 00:30 推遲到 00:37:20 開始。

### 2.5 掛車階段：每方向獨立班距脈衝（正線優先）

識別碼：`periodic-directional-headway-eat-v1`

班距的學術定義是**同方向（同路線）相鄰兩班的發車間隔**。引擎為每條正線路線各自生成一條班距脈衝流，掛車時只派給「輪替正好輪到該方向」且準點空閒的車輛。

- 準點掛不上時：
  - 該方向**已有前班**：只要延後不跨越下一脈衝即可掛上（吸收累積遲到，避免 D0538→D0552 跳成 14 分）
  - 該方向**尚無前班**：最多延後 120 秒（避免開班把脈衝拖離格位）
- 跨時段：新時段第一脈衝 ≥ 上一班同方向 + max(舊班距, 新班距)
- 掛車同方向班距下限：上一班實際發車 + **max(前班時段班距, 本班時段班距, 車隊物理班距下限)**（與驗證一致；300→180／180→300 都守較嚴者）
- 開班時回程方向尚無車可掛 → 略過早期脈衝，下一格再試
- 模板正線視窗是服務承諾，不是硬性最早出車時刻。若視窗前緊接整備，該 row 的可出車起點可向前延伸至 `max(整備開始, 正線開始 − 讓渡餘裕)`，使車輛在正線開始前承接脈衝並完成預出車。
- 交接最佳化以車隊服務連續為目標，不要求同批完成整備的每台車在整點同方向同時發車；同方向仍必須依班距交錯。

這修正了舊算法「一條全域脈衝被兩方向共用」造成的 D0030→D0040→D0110 跳格。

### 2.6 整備次於正線

非正線任務可由正線從兩側壓縮：

- **整備開頭**：正線回程延後整備開始，鎖住原規劃結束時間（例：14:00–15:00 充電、車 14:02 才回 → 14:02–15:00）。
- **整備尾端**：為使下一個正線視窗開始時已有服務能力，引擎可在讓渡餘裕內預出車，整備開始不變、結束裁到首班發車。

只裁剪與正線直接相鄰的整備，不跨模板空白，不平移其他任務。不得為了塞滿整備而砍掉回程。

### 2.6.1 正線優先讓渡餘裕（班表 `entrySlackBySection`）

在**建立正線班表 Step 2**，依選定整備任務已啟用的區段（充電／洗車／保養／行前／機動）分別填寫；預設 **600 秒**。屬班表策略參數，**不寫入整備任務本體**。同一設定對整備兩側分別生效：

1. 正線最多可占用整備開頭的秒數。
2. 下一正線視窗最多可提前此秒數結束整備並預出車。

兩側各自受此上限約束，不共用總額。改動後班表產出視為過期，須重新生成。

掛車開新輪時：若「發車＋整輪來回結束」會晚於「整備開始＋此餘裕」，則不硬發；在餘裕內結束則可發，整備開始再依正線優先延後並鎖尾壓縮。後面沒有整備則不套用整備切入閘門。已開輪的回程仍可由週期補完吃進整備開頭。

整備後緊接正線視窗時，引擎將該 row 的可出車時間向前延伸，但不得早於整備開始，也不得跨越空白或其他任務。首班確定後，整備尾端裁到實際首班發車。

### 2.6.2 空時段正線讓渡餘裕（班表 `emptyIntervalMainlineSlackSeconds`）

時間模板在 00:00–24:00 內若存在未排定任何時間屬性的空時段，建立班表 Step 3 需填寫此值（預設 **600 秒**）；全日皆有屬性覆蓋則不顯示。

語意：**只允許占用空時段開頭**（正線視窗結束後，回程／開新輪可往後占用相鄰空時段開頭最多此秒數）。**禁止**提前占用正線開始前空時段的尾端出車。

改動後同樣使班表產出失效並需重新生成。

### 2.7 其他閘門

| 代號 | 意義 |
|------|------|
| `ANCHOR_CONFLICT` | 正線結束撞上下一正線錨點 |
| `TIMELINE_OVERLAP` | 同線任務重疊 |
| `ROTATION_CYCLE_INCOMPLETE` | 時間線未跑完路線群組一整輪（例：只下行未上行） |
| `HEADWAY_PHYSICAL_IMPOSSIBLE` | 同路線相鄰發車短於車隊物理班距下限 |
| `HEADWAY_BELOW_TARGET` | 實際間隔低於兩班時段班距的較嚴者（warning） |
| `INSUFFICIENT_TIMELINES` | 時間線數可能撐不住班距（warning） |
| `TURNAROUND_LIMIT_EXCEEDED` | 單路線超過折返時限 |
| `CLOCK_ALIGN_VIOLATION` | 錨點未落在 10 秒格 |
| `STATION_LEG_TRAVEL_INCOMPLETE` | 缺拓撲站間時間；站點時刻均分估算（warning） |
| `STATION_LEG_TRAVEL_INVALID` | 站間時間非法（負值或 min＞avg） |

## 3. 算法流水線

```
normalizeInput
  ├─ 依班距為**每方向**各自生成發車脈衝（S3 對齊；跨時段取 max(舊,新) 班距銜接）
  ├─ 依相鄰整備讓渡餘裕向前擴展可出車視窗
  ├─ 掛到輪替正好輪到該方向、且準點空閒的時間線（交接前可預出車）
  ├─ 跨正線視窗時將輪替推進至完整循環邊界
  ├─ 合併非正線任務
  └─ 週期補完（來回＋同方向班距對齊；無合法回程則撤回未成輪自動去程）
       ↓
assignRoutes（執行順序硬輪替＋占用含 S4）
       ↓
expand（寫入區塊；正線可裁剪整備頭尾，裁剪完成後才建立最終區塊）
       ↓
validate（S1+S2 相加、班距、重疊、折返…）
       ↓
plan + report
```

| 模組 | 檔案 |
|------|------|
| 正規化／掛車／補完 | `normalizeInput.ts`, `generateDepartures.ts`, `completeRotationCycles.ts` |
| 物理量 | `physics.ts`（含 `resolveInterTripGapSeconds`） |
| 路線指派 | `assignRoutes.ts` |
| 展開 | `expand.ts` |
| 驗證 | `validate.ts` |
| 站間 leg／逐站時刻 | `../stationLegTravel.ts`, `../buildBlockStationDepartures.ts` |
| 入口 | `generate.ts` |

算法識別碼：

- 時刻生成：`periodic-directional-headway-eat-v1`
- 路線指派：`constraint-greedy-v1`（現行＝硬輪替）
- 週期補完：`rotation-cycle-completion-v1`

## 4. 2026-07-17 修復重點

| 問題 | 舊行為 | 新行為 |
|------|--------|--------|
| D0010→U0017 只隔 30 秒 | `max(恢復, 換線)` | `恢復 + 換線` |
| 第六列只有下行 | 無來回約束 | 週期補完強制整輪 |
| 路線順序可被貪婪改掉 | 軟偏好 −100 | 硬輪替 |
| 各層空檔公式不一致 | 掛車／指派／驗證各算各的 | 統一 `resolveInterTripGapSeconds` |
| 長時段延後搜尋空轉 | 每 10 秒掃一次 | 直接跳到最早可行時刻 |
| 回程 U0018 與 U0020 只差 2 分鐘 | 回程只看物理最早發車 | 回程對齊同方向班距；正線優先，充電推遲 |
| 掛車可造成同方向班距不足 | 只看車輛釋放時間 | 每方向獨立脈衝；準點掛不上則略過 |
| D0030→D0040→D0110 班距跳格 | 一條全域脈衝被兩方向共用 | 每方向獨立班距流；下行穩定每 600s |

## 6. 已知限制

1. **收班前最後回程**：自動掛車若日界內塞不下合法回程，會撤回尚未成輪的末班去程。人工固定班次仍可能需要營運者調整。
2. **無全局回溯**：不任意移動理想班距脈衝；時間線不足時會延後或略過，服務缺口由最終 PPHPD 趨勢與等效班距呈現。
3. **跨時段脈衝相位**：不強制每個整點都有脈衝；交接由整備尾端預出車維持車隊服務連續。
4. **拓撲 leg 快照**：班表草稿的 `stationLegTravels` 在選路線時寫入；地圖之後改拓撲不會自動更新舊草稿（須重選路線）。詳見 [點位拓撲規格 §5](點位拓撲規格.md)。
5. ~~週期補完缺同車後續檢查~~：已於 2026-07-19 補上整備前上限與同車後續空檔；見 [排班引擎規則.md](排班引擎規則.md)。
